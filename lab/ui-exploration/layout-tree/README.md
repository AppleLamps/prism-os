# Layout tree: Clay-style layout as circuit layers

## What it is and how to run it

This folder asks how far a flexbox-like, Clay-like layout engine goes when it is written as circuit layers. A static tree of rows, columns, wrapping rows, grids, scroll containers, boxes and texts compiles into one Indirect circuit that runs Clay's passes in order: fit widths, widths (grow and shrink with min and max), text line counts, fit heights, heights, and positions. The tree's shape and constants are fixed at compile time. At runtime only the viewport size, scroll positions, a sidebar width driven by a spring, and prepared text tables change. A separate JavaScript implementation of the same algorithm, written with ordinary loops, checks every result.

Run from the repo root:

- `bun test lab/ui-exploration/layout-tree` runs 9 tests in about 0.3 s: water filling on random children, the greedy text tabulation, 60 random trees at 15 viewports each against the JS reference, a row of 16 grow texts at 401 viewport widths (including widths where some text sits strictly inside its shrink interval and widths where some text sits strictly inside its grow interval), and 5 app shell tests (frames against the reference, grid reflow, the sidebar toggle through its spring, frames of 100 ms, sticky headers).
- `bun lab/ui-exploration/layout-tree/report.ts` prints every table in this README and writes `report-results.json`. It takes a few seconds.
- `bun lab/ui-exploration/layout-tree/demo.html` opens the app shell in a browser. Click the black menu button to toggle the sidebar, scroll the cards with the wheel, and resize the window to see the grid reflow and the text rewrap.
- `bun lab/ui-exploration/layout-tree/prepare-text.ts` regenerates `app-text-tables.ts` from the pretext copy in the scratch folder with a deterministic fake canvas, and checks the tables against pretext's own line counts.
- `bunx tsgo -p lab/ui-exploration/layout-tree` type-checks the folder.

numeric-ui-core.ts is unchanged. `TaggedCircuit` in circuit-tools.ts subclasses `Circuit` only to record which pass and tree level created each operation, so the report can split the compiled program.

## What was built

Files:

- `tree.ts`: node types and constructors, and the full layout semantics in one comment at the top. Sizing kinds are Clay's `fixed`, `percent`, `fit` and `grow` (with min and max), plus `input`, a size that comes from a runtime value, e.g. the sidebar width a spring produces. Containers have padding, a gap, `alignX`, `alignY`, and a layout: `row`, `column`, `wrap` (flex-wrap) or `grid` (equal columns, like CSS `repeat(auto-fill, minmax(220px, 1fr))`). Columns can scroll vertically. A node whose parent is a column strictly inside a scroll container can be sticky. A sticky flag anywhere else, e.g. on a direct child of the scroll container, has no effect.
- `builder.ts`: allocates source cells for inputs and text tables, and compiles the tree pass by pass.
- `ops.ts`: exact comparisons, clamps, the reciprocal of a small integer count, and water filling.
- `reference.ts`: the float64 JS layout, plus a port of Clay's own GROW loop for comparison. It shares only the node types and the `fitEpsilon` constant with the builder. It has its own code for which children may shrink, the alignment factors, and when a sticky flag applies, so a mistake in the builder's versions of those rules would show up as a mismatch.
- `text-table.ts`: turns a line-count function into a staircase of widths by sampling and bisection, and a greedy word wrap for the browser's prepare step.
- `app-shell.ts`: the app shell tree and its circuit (the menu button's toggle, the sidebar spring, the layout and the scroll clamp), and a per-frame machine that writes each frame's inputs into the source table, runs the circuit and copies the next-source outputs back.
- `app-text-tables.ts`: the app shell's text tables, generated by `prepare-text.ts`.
- `random-tree.ts`, `compare.ts`, `circuit-tools.ts` (source table allocator, tagged circuit, split of a compiled program by tag, a seeded random generator).
- `layout.test.ts`, `app-shell.test.ts`, `report.ts`, `prepare-text.ts`, `demo.html`, `demo.ts`, `demo.css`.

How each part of the algorithm becomes atoms:

1. Fit sizes, children first. Sums of children are affine. The widest child is a tournament of `max(a, b) = b + relu(a - b)`, one ReLU per pair. Constants fold, so a box with a fixed size costs nothing.
2. Grow and shrink with min and max. Clay distributes leftover space in a loop until it converges. A circuit cannot loop, and sorting the breakpoints costs n² comparisons plus routing. The builder instead evaluates the total at each child's own breakpoints. With `E(p) = Σ_k relu(p - low_k) - relu(p - high_k)`, which is the total at level p minus the sum of lows:
   - `atLow_i = [E(low_i) >= excess]` means the level sits at or below this child's low.
   - `atHigh_i = [E(high_i) <= excess] and not atLow_i` means the level reaches this child's high.
   - Every other child is free, and the level is `(excess - Σ atHigh_i (high_i - low_i) + Σ free_i low_i) / freeCount`. `1 / freeCount` is a masked sum over the exact one-hot of the count, so it equals `fround(1 / count)`.
   - `size_i = low_i + atHigh_i (high_i - low_i) + free_i relu(level - low_i)`.

   Grow uses low = fit width and high = max. Shrink uses low = min width and high = fit width. Outside its own regime, each formula returns the fit width, so the builder adds both without a select. The pairwise ReLUs are shared: `relu(b - a) = relu(a - b) - (a - b)`. When FP32 flips a bit near a tie, sizes change continuously, e.g. a child that should be free at level 120.0001 gets clamped at its low of 120. So FP32 drift in these bits only shows up as drift in sizes.
3. Cross-axis sizes are min and max, following Clay: a grow child takes `max(minWidth, min(inner, max))`, and a fit child takes `max(minWidth, min(fitWidth, inner))`.
4. Wrap is a scan over children: `fits_i = [inner + ε - used_(i-1) - gap - width_i >= 0]`, `offset_i = fits_i × (used_(i-1) + gap)`, `used_i = width_i + offset_i`. Line heights are a running max that resets where a line starts. A backward scan gives each child its line's final height and used width (for per-line alignment), and a running sum gives line tops.
5. Grid: the bits `[inner + ε >= c × minCellWidth + (c - 1) × gap]` for c = 2..maxColumns, and their differences as a declared one-hot over column counts. The cell width is `(inner + gap) × Σ_c [columns = c] / c - gap`. For each column count the row structure is static, so row heights are static max tournaments and row tops are static sums. A child's height and top are masked reads over the one-hot, which the compiler lowers to gathers.
6. Text: `lines = baseLines + Σ_k [width < threshold_k]`, 4 atoms per threshold cell.
7. Positions: one prefix-sum affine per child. Main-axis alignment is `factor × relu(leftover)`. Scroll is `min(input, relu(contentHeight - height))`. Sticky is `max(naturalTop, min(scrollContainerTop, parentInnerBottom - height))`.

Every decision uses the 4-atom comparison from phase 1, a boolean atom on a difference scaled by 256 and clamped, which holds for differences up to 16,384 px. Wrap and grid "does it fit" decisions allow a 1/64 px fit epsilon, like pretext's `lineFitEpsilon`. The section on awkward parts explains why.

The app shell (`app-shell.ts`) has a header with a menu button, a title, a spacer and three buttons. Below it, a body row holds a sidebar whose width comes from a spring, and a scrolling main column. The main column holds a wrapping row of 10 tags, then two sections, each with a sticky header and a grid of cards. A card has a thumbnail, a title, a caption, a spacer that grows so the meta rows of cards in the same grid row line up, and a meta row. A footer sits at the bottom. The tree has 186 nodes and 80 texts. Each frame the circuit hit-tests the menu button against the rectangle from the previous frame (4 source cells, the way immediate-mode UI hit-tests what the user saw). It then toggles the open bit and sets the spring destination to `220 × open × [viewportWidth >= 640]`. It steps `emitSpring`, takes `relu(position)` as the sidebar width, and runs the layout. The next-source cells are the open bit, the spring state, the menu button's rectangle, and the clamped scroll position.

The demo prepares text in the page: it measures words with canvas in the page's font, tabulates line counts with the greedy word wrap, and writes the staircases into the source table once. After that, each frame JS writes the viewport size, wheel deltas, pointer presses and frame time into source cells, runs the circuit, and copies rectangles onto nested absolutely positioned elements.

### Text tables

`prepare-text.ts` tabulated the app shell's 80 texts with pretext and the fake canvas in 17 ms, producing 153 thresholds. The staircases matched pretext's `measureLineStats` line counts at all 40,306 checked widths, including 1e-4 px on each side of every threshold.

### Clay's GROW loop against exact water filling

Clay raises the smallest growing children toward the second smallest by at most the leftover space divided by all growing children, so it approaches the level geometrically and stops when less than 0.01 px is left. The port follows clay.h: it computes in float32, and it treats sizes within 0.01 px of each other as equal (`CLAY__EPSILON` in `Clay__FloatEqual`). Over 1,000 random rows per size:

| grow children | average rounds | max rounds | max size difference px |
| --- | --- | --- | --- |
| 2 | 5 | 14 | 0.00992 |
| 4 | 9.94 | 113 | 0.00997 |
| 16 | 20.7 | 104 | 0.00981 |
| 64 | 52.5 | 226 | 0.00937 |

Unrolling Clay's loop into layers would need a bound of hundreds of rounds and would still be off by up to 0.01 px. Water filling needs no rounds: 9 to 13 layers in the child-count rows above.

## What this shows about how far the approach goes

### What fit well

- Clay's pass structure over a static tree maps directly onto layers. Fit sizes are sums and maxima, positions are prefix sums in one layer, and alignment, scroll clamping and sticky headers are a few ReLUs each. In the nesting test a tree level costs about 4 layers and 12 live ops.
- Grow and shrink with min and max, the part Clay solves with a loop, became a direct solve whose depth doesn't grow with the child count: in the widths pass, 9 layers for grow boxes with constant fit widths, 12 for grow containers with runtime fit widths, 11 for shrinking texts and 13 for grow texts, at every count from 2 to 64. The cost moved into width, and it grows like n² once the breakpoints are runtime values, e.g. 5,601 live ops and 33,141 stored weights for 64 grow containers, and 9,156 ops and 50,946 weights for 64 shrinking texts. Rows in real UIs have 2 to 8 children, where a whole one-container circuit costs 32 to 501 live ops.
- Discrete results that must be exact bits are exact. Text line counts, wrap line membership and grid column counts had 0 mismatches over 48,420 results on random trees, 29,348 in app shell frames, and every width sweep in the child-count table. Positions drifted at most 0.0004 px in random trees and app shell frames. In the widest rows the drift reached 0.013 px, and it comes from adding many widths in FP32, not from the water fill.
- Grids with auto-fill columns cost at most 15 layers at any child count. The one-hot over column counts turns row lookups into gathers (28 gather reads in the app shell), so a child's height and top store no weights.
- Text heights join the layout as comparisons against pretext's tabulated thresholds, which matched pretext at every width checked.
- A whole app shell with a spring-driven sidebar, two grids of cards with text, sticky headers, a wrapping tag row and scrolling is 2,806 live ops, about half of IndirectOS.

### What got awkward

- Flex-wrap is a scan. Its depth grows about 4 layers per child in the wrap test (276 layers at 64 children), and more when children's heights are runtime values: the 10 tags alone put 59 layers on the app shell's longest chain. The parallel reformulations are the same as for text line breaking (count where a line starting at each child would end, then follow those pointers). Phase 1 measured them as much wider (pretext.md, section 5.3), and I did not build one.
- Depth adds up through fit content. A parent's grow or shrink decision reads its subtree's fit sizes, and a child's size or position may read the parent's decision. So the deepest scan in a subtree reaches every rectangle whose size or position reads an ancestor's decision over that subtree. For example, the body row's height reads the tags scan through the scroll container's content height, even though that content always overflows. Every rectangle inside the scroll container reads the scroll offset, whose clamp reads the container's height, which comes from the body row's height. 162 of the 185 rectangles below level 0 read the body row's height and sit at layers 109 to 115. The header's contents and the sidebar's nav rows don't, and stay at layers 1 to 30.
- A spring that feeds the same frame's layout stacks its depth under the whole layout: 39 layers before the layout starts. Reading the previous frame's spring position gives 83 layers, and removing the tags wrap as well gives 48.
- Ties are systematic, not rare. A fit-width wrap container is exactly as wide as its content on one line, so its last child always sits on a tie between two sums that FP32 rounds in different orders. Before the 1/64 px fit epsilon, 6,000 random layouts produced 8 discrete mismatches and one 400 px jump. With it, they produced none.
- FP32 accumulation hides in derived constants. My first `1 / count` was a telescoping sum of threshold bits, whose relative error of a few 1e-6 became 0.34 px of drift across 64 growing children once multiplied by a numerator near 3,500. A masked sum over an exact one-hot has exactly one nonzero term. With it, the 64 grow boxes drift at most 0.0086 px over the width sweep, at the last child's x, while their widths drift at most 0.0000076 px.
- Sentinel values need care around negative sizes. Unused threshold cells first held 0, which counted as extra lines when a text's width went negative (a percent child of a container whose padding exceeds its width). Unused cells now hold -8192.
- Constant folding collides with one-hot declarations. A grid whose inner width is a compile-time constant folds every column bit into the same constant wire, which `assumeOneHot` rejects, so the builder resolves the column count at compile time in that case. Phase 1 hit the same hazard with constant seeds.
- Text capacity is a worst case. The source table reserves one threshold cell per word, because another font gives a text a different number of thresholds. With the fake canvas only 153 of 284 cells are used, and the unused comparisons cost roughly (284 - 153) × 3.6 ≈ 470 live ops of the 1,013 in the text pass.
- The builder needs every input wire before the layout starts. So the menu button's hit test reads the previous frame's rectangle from 4 source cells, not this frame's layout, even though the header doesn't depend on the sidebar.
- Not built: grow inside wrap lines (CSS flex-grow per line needs one water fill per line with runtime membership), shrink in proportion to each child's basis like CSS `flex-shrink` (the level would divide by a runtime sum instead of a count, which needs general division: 69 ops and 20 layers in phase 1), horizontal scrolling, floating elements, aspect ratios, and percent sizing that follows Clay exactly for the root.

### What stayed outside the circuit

- The prepare step: segmenting and measuring text, then tabulating line counts by bisection. Headless it uses pretext with a fake canvas; the browser demo uses canvas `measureText` and a greedy word wrap.
- The DOM projection: nested transforms and sizes, font loading, and the browser's own line breaking inside each text box. The demo relies on the canvas staircase agreeing with the browser's line breaks, which I did not verify, since nobody was awake to grant browser automation. A later Chrome check found the browser's line breaks agreeing with the staircase for all 80 texts, see [Browser check](#browser-check).
- Event plumbing: JS accumulates wheel deltas into the scroll cell and keeps the cell within its declared range of 0..8192, records press coordinates, and measures frame time. The circuit clamps the scroll position to the content's bottom and writes it back.
- The tree's structure. Children cannot appear or disappear at runtime. A list whose length changes would need a fixed capacity plus presence bits, and changes of structure would need the constructions in outside-techniques.md.

## Open questions and next steps

- Parallel wrap: build the next-start counts (depth about 4) with one gather per line, and measure against the scan. An integer-index read instruction (phase 1's missing instruction) would make the pointer following cheap.
- Which values should come from the previous frame? The spring and a scroll container's content height are the obvious candidates. The depth variants show the potential (115 to 48 layers), but the visible cost of one frame of lag during resizing isn't measured.
- Real fonts: compare the circuit's line counts with the DOM's wrapped heights over many widths in a browser harness.
- Animate layout changes by putting a spring on every rectangle, using the shared spring matrix from phase 1, so cards glide when the grid reflows.
- Express chenglou.github.io's gallery (1 to 7 columns with per-row max heights) and nicer-hacker-news's thread (a column of texts with sticky user banners) with this builder, and compare with the trace compiler's slices.
- Code generation from the compiled program (about 10× faster than the executor in phase 1) should bring the app shell from about 24 µs to a few µs.
- Tighter text tables: texts whose widths are the same wire, e.g. every caption in a grid, could share one sorted set of threshold comparisons.

## Browser check

2026-09-13, Chrome, served with `bun lab/ui-exploration/layout-tree/demo.html`.

- The page loads with no console errors, with 5 grid columns in a 2,320 by 1,268 px viewport. The stats show 2,806 live ops, 115 layers and 7,451 stored weights, and the text prepare step took 5 to 15 ms.
- Clicking the menu button springs the sidebar from 220 px to 0 and back. The cards widen and narrow, and the captions rewrap.
- The canvas staircase agreed with the browser's own line breaks. For all 80 texts, the number of lines the DOM draws equals the circuit's box height divided by the line height. - First check: any frame of 32 ms or longer stopped the page with "source wire 9 is outside its assumed range". The machine in `app-shell.ts` clamps the frame to 32 ms and writes a quarter of it into the `spring.timestep` cell, whose declared maximum was 0.008, but the Float32Array stores 0.008 as 0.0080000004. The first fix capped the frame duration in `demo.ts` at 31.9999 ms, which left `step` throwing for any other caller with a `frameDuration` of 0.032 or more.
- Fixed in `app-shell.ts` instead: the cell's declared maximum is now `Math.fround(0.008)`, the value the Float32Array stores, and `demo.ts` passes the measured frame duration again. A new test in `app-shell.test.ts` presses the menu button and then steps 120 frames of 100 ms: the stored timestep is 0.0080000004, the sidebar closes, and every frame's discrete results match the JS reference. Before the change, that test threw the same error. The counts in this README didn't change: live ops, layers, stored weights, widest layer and gather reads of all four depth variants, and the split by pass and tree level, came out identical before and after. `bun test lab/ui-exploration/layout-tree` (9 tests) and `bunx tsgo -p lab/ui-exploration/layout-tree` pass.
- Recheck in Chrome, with `requestAnimationFrame` replaced by a scheduler that runs a frame every 100 ms: no errors. The tab's viewport was 406 by 422 px this time, under the 640 px breakpoint, so the sidebar sprang closed on load. In a 1,280 by 800 px iframe of the page, the menu button closed the sidebar over 11 frames of 100 ms (220, 160, 92.1, 47.4, 22.8, 10.4, ..., 0 px) and opened it again (0, 60, 127.9, 172.6, ..., 220 px).
