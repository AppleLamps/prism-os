# Index read: reading a table at an exact integer index

## What it is and how to run it

This prototype adds a direct read at a computed integer index to Indirect's numeric runtime, then re-measures UI workloads that need one. The workloads are `values[index]`, recovering pretext's line starts from a next-start table, virtualized and filtered lists, and 1D photo strips at a focused index. It also lets gather lowering see through products of bits, so the exact selections in lab/event-window lower to gathers.

The runtime here is a modified copy of the repo root `numeric-ui-core.ts` (commit a915dcb), kept in this folder as `numeric-ui-core.ts`. The repo root file is untouched. Every addition is described below and listed at the top of the copy.

Update, September 14, 2026: the repo root `numeric-ui-core.ts` now has an index read instruction based on this prototype ([execution-model.md](../../../execution-model.md#index-reads), and decision 1 in [the guide's decision record](../guide/review-and-decisions.md#1-should-the-shared-runtime-get-an-index-read-instruction)). These parts of the copy weren't added: the compile pass that recognizes relu one-hots (`lowerIndexOneHots`, section 2), and `assumeBit`, `inferBitFamilies` and `lowerSelects` from section 3. Below, "the shared runtime" means the root runtime at commit a915dcb.

Run from ~/github/indirect:

- `bun test lab/ui-exploration/index-read`: 25 tests, under one second.
- `bunx tsgo -p lab/ui-exploration/index-read`: typecheck.
- `bun lab/ui-exploration/index-read/report.ts`: every measurement in this README, about 30 seconds and 3 GB of memory, mostly spent building the dense constructions. Pass part names to run some of them, e.g. `bun lab/ui-exploration/index-read/report.ts lines list`. The parts are table, lines, list, variable, compaction, strip, thumbnails, floor, depths, and event-window. Results merge into `report-output.json`.
- `bun lab/ui-exploration/index-read/demo.html`: a browser demo with a 10,000-row list filling 24 DOM slots, with a menu to switch between circuits, and a 221-photo strip centered on the focused photo. The logic is in `workloads.ts`, which the tests cover. I checked that the page bundles with `bun build`, but I haven't looked at it in a browser, since browser automation needed a permission nobody was awake to grant.

`pretext-fixture.json` holds prepared segment widths and kinds for three paragraphs (63, 255, and 1,023 segments), and pretext's own line results at sampled widths. It was generated by `bun scratchpad/phase2/index-read/pretext-fixture.ts` from phase 1's copy of pretext's src, with the fake canvas (Blink profile, widths in 64ths of the font size). The tests and the report read the fixture, so they never import pretext.

## What was built

### 1. The index read instruction

`circuit.indexRead(index, candidates, {outOfRange})` and `circuit.indexReadAffine(indexTerms, indexBias, candidates, below, above)` append an index read, a fourth instruction next to affine, reglu, and boolean. `emitIndexRead` isn't a separate function; these two methods are the builder API.

The contract:

- **Definition.** Both evaluators compute the index form with the usual FP32 accumulation, take `position = floor(index)`, and copy the FP32 value of `candidates[position]` into the output. The index form is a wire or an affine, e.g. `[[firstRow, 1]]` with bias 3 for the fourth visible row, and small affine producers compose into it the same way they compose into a reglu gate. No rounding step touches the copied value, so `-0`, `Infinity`, and `NaN` come through unchanged.
- **Outside the table.** Each side has its own rule. `'clamp'` reads the nearest end, e.g. index -5 reads `candidates[0]`. `'zero'` reads +0, e.g. a line walk whose start has reached the end of the text reads a width of 0. `indexRead` uses one rule for both sides, and `indexReadAffine` takes them separately. A NaN index reads NaN.
- **What the index must satisfy.** The instruction accepts any FP32 index: floor and the range checks run in float64 on an FP32 value, so they can't round. The promise that makes the read equal to a relu one-hot plus a masked sum is that the index holds an exact integer, so floor changes nothing. `validateIndexReads(circuit, values)` checks that promise in tests. A fractional index is where the two constructions part ways: the relu one-hot interpolates, e.g. index 1.5 gives half of row 1 plus half of row 2, while the instruction reads row 1.
- **Candidates.** No declared range is required. A candidate may be infinite, may repeat (e.g. `[a, a, b]`), and may be any earlier wire. The dense construction needs finite candidates, because an unselected `Infinity * 0` turns its sum into NaN, while the instruction only reads the selected value. So the two constructions also differ exactly where a candidate may be infinite, and a test pins that difference.
- **Build-time rules.** A constant index selects its candidate at build time. Identical reads return one wire. The output range is the union of the ranges of the candidates the index range can reach, plus 0 where a zero side is reachable. Depth is one more than the deepest of the index operands and the candidates.
- **Gradient.** The selected candidate receives the output gradient, so a table of values can be trained. The index is a step function: its derivative is 0 between integers and undefined at them. `backpropagateReference` rejects a gradient into the index by default, as it rejects boolean gradients. `{indexGradient: 'zero'}` propagates nothing into the index. `{indexGradient: 'backward-difference'}` propagates `read(i) - read(i - 1)` at integer `i`, which is exactly what the reference backward pass gives the relu one-hot construction. A test compares the two on every source wire at every integer index from -3 to count + 2, for both one-hot styles.
- **Execution.** In a tensor layer an index read is one output row with no weights, plus one projection row that holds the index form, placed after the gate rows. After the sparse matmul, the executor floors that row and copies the candidate's packed value. The candidate table is stored as a base position and a stride when the candidates sit evenly spaced in packed storage, e.g. a column of source cells, or a table computed in one loop that interleaves with another. Otherwise it stores one position per candidate, and reads with identical position lists share one array.

### 2. Recognizing a relu one-hot and resolving it from its index

Existing circuits build reads at a computed index from relu one-hots, e.g. `[x >= j] = relu(x - j + 1) - relu(x - j)` and member `j = [x >= j] - [x >= j + 1]`, then masked sums. `compileTensorProgram(roots, lowerGathers, {lowerIndexOneHots: true})` checks every declared one-hot group that a lowered masked read uses, and resolves the group from its index wire when all of these hold:

- Every member expands, through ordinary or preserved affines and plain relus, to integer weights over `relu(x + integer bias)` of one wire `x`, with total weight at most 4.
- At every integer `x`, every member is exactly 0 or 1, and member `p` is 1 exactly at `x = low + p`. The first member may also be 1 for every `x` below the table, which becomes a clamp on that side, and likewise the last member above.
- `x` has a declared range within ±2^21, so every relu value is an exact integer.

Given the declared one-hot contract, `floor(x)` then selects the same member as the bits. The executor computes `floor(x) - low` in float64 once per group per evaluation, instead of a dot over N bits. The ramps, members, and products that nothing else reads leave the compiled program.

Both phase 1 styles are recognized: constructions.ts's `values[index]`, which clamps on both sides, and the pretext circuits' `integerOneHot`, which clamps below and reads zero above, including pointer jumping's windowed one-hot of `jump[s] - s`. Tests show the pass declining an index coefficient of 2, an index range wider than 2^21, members declared out of order, and thresholds at half integers. When members are read elsewhere, the reads still resolve from the index, but the members stay live.

### 3. Gather lowering through products of bits

The shared runtime lowers a masked sum only over a declared group. `emitFirstActive` declares its group only when its gate and candidates are proven bits, and a proven bit is only a boolean atom, a declared group member, or a range pinned to 0 or 1. event-window's selections are built from products like `hit * maximized`, so nothing lowers there.

The copy adds:

- `circuit.assumeBit(wire)` declares an exact bit. Source cells declared this way are checked on every evaluation, next to their ranges.
- `isProvenBit` follows how a wire was built. A wire is a proven bit when it's one of:
  - a declared bit, a boolean atom, a group member, or a range pinned to 0 or 1
  - `multiply(bit, bit)` or `select(bit, bit, bit)`
  - `1 - bit`, written as bias 1 minus the bit, or as a wire pinned to 1 minus the bit
  - the sum of an at-most-one family

  Each affine now keeps its authored terms, so provenance can see what a small sum was built from after the builder composed it into consumers.
- An at-most-one family is a set of proven bits of which at most one can be 1. The recognized shapes are:
  - members of one declared group, or disjoint sums of such members, e.g. `hit[i] = routed[i] + routed[i + 4]`
  - `{bit, 1 - bit}`
  - selects that share one proven gate, over two families
  - products that share one proven bit, over a family
- When a sum of exact multiplies matches no declared group, but its masks form a family, the masks become a group for that compile, and the sum lowers to a gather.
- `{lowerSelects: true}` also lowers every select with a proven gate as a two-member read. It's off by default and counted separately below.

`event-window-circuit.ts` is lab/event-window/circuit.ts with its imports pointed at this runtime, plus declarations in exact mode. It declares the down, move, and up event cells, pressActive, pressOnTitle, pressWasFocused, pressOnMaximized, slopLatch, everPressed, and the four maximized cells as bits. It also declares the press rectangle record and the four focus cells as one-hot groups that allow all zeros. The oracle only ever writes 0 or 1 into those cells.

### 4. Compile changes the reads needed

- **Depths after lowering** (`recomputeDepths`, on by default). The shared runtime places each live operation at its build-time depth. A lowered read no longer waits for the products it replaced, so the copy recomputes each live operation's depth from what it reads after lowering. The "bit gather" rows below keep build-time depths, to mirror the shared runtime.
- **Evenly spaced and shared candidate tables**, described in section 1. They matter because a table is O(N) integer bookkeeping per read otherwise.

### Floor division before a read

`bun lab/ui-exploration/index-read/report.ts floor` checks `floor(fround(fround(1 / rowHeight) * scrollTop))` at every multiple of the row height up to 2^21, and one below each. It misses at least one row for 74 of the 512 integer row heights from 1 to 512, e.g. height 41 at scrollTop 41 gives row 0. `emitFloorDivide` rounds the approximate quotient, then subtracts 1 when the exact integer remainder is negative. It's 8 live operations and 7 layers, with 0 mismatches on the same points for the first ten failing heights.

## What this shows about how far the approach goes

### What fit well

- **Reading at a computed integer no longer grows with the table.** `values[index]` over 10,000 entries is 1 live operation in 1 layer, down from 30,002 with the shared runtime's bit gather. The instruction and the recognition pass reach the same count. The recognition pass gets there for circuits already written with relu one-hots, e.g. phase 1's pretext circuits, without rewriting them.
- **Pointer following over a computed table is cheap.** Once the next-start table exists, recovering every line start of the 1,023-segment paragraph costs 1,409 more live operations, about 9 per line slot, instead of 483,399, and it matches pretext at every checked width. Pointer jumping, which phase 1 estimated at 7 to 10 million atoms, is 35,914 operations beyond the table, in 66 layers. Each level reads at a computed index once per start, so the work is O(segments × log lines). What's left is dominated by the next-start table itself: 190,279 operations for 23 comparisons per start.
- **Virtualized rows cost what the slots cost, not what the data costs.** 24 slots with 3 fields over 10,000 rows is 153 live operations, 9 layers, and 204 stored weights, the same as over 1,000 rows. The row count only shows up in the size of the source table.
- **Binary search becomes a practical pattern.** With reads at O(1), a search over sorted prefix sums is log2(N) reads, comparisons, and additions. It finds the first visible row of 10,000 variable-height rows in 215 operations and 57 layers, versus 30,143 operations for counting rows. The same pattern turns a filtered list into prefix counts plus one search per slot. That's 10,000 operations and 19,396 stored weights for 1,000 items into 20 slots, versus 81,961 operations and 660,424 stored weights for compaction, and it reaches 10,000 items at 125,324 operations.
- **Constant tables at a focused index move from weights into cells.** At 1,024 photos, Photos' thumbnail targets take 1,063,936 stored weights and 918 µs as constants per focus. As a table of 2 × 1,024 cells per field, read once per thumbnail, they take 3,072 stored weights and 30 µs, with identical outputs.
- **Decisions stay exact.** A read copies an FP32 value with no rounding step, so integers and bits read through a table stay integers and bits. For example, the line walk reads integer starts and compares them with exact relu differences.
- **A handful of provenance rules is enough for event-window.** The copy lowers 11 reads where the shared runtime lowers 0, or 42 with selects, with 0 mismatches over 20,000 frames on every live wire and against the oracle.

### What got awkward

- **Sequential walks are still deep.** Line recovery reads start after start, about 3 layers per line: 490 layers for 157 line slots, more than twice IndirectOS's 192. Pointer jumping brings it to 66 layers for 18% more operations. The index read removes width from a walk, not depth.
- **The recognition pass builds the one-hot before removing it.** Building takes 776 ms against 131 ms for the instruction at 1,023 segments, and 561 ms against 9 ms for the 10,000-row list. The report's 3 GB peak comes mostly from these built graphs.
- **Build-time depths hide what lowering removed.** Lowered reads keep the depth of the products they replaced, so the compiler has to recompute depths from what live operations read. That takes 1,023-segment recovery from 744 to 490 layers; the bit gather alone only goes from 850 to 801.
- **Tables are integer bookkeeping that can grow quietly.** A table costs O(1) when its candidates sit evenly spaced in packed storage or it's shared, and O(N) per read otherwise. Pointer jumping first stored 1,854,682 table entries at 1,023 segments, because every window touching the end included an absorbing constant. Dropping that entry made it 0. The recognized one-hot virtual list still stores 690,000 entries, because each slot's column is padded with zero cells.
- **The index has to be an exact integer, and floor isn't free.** Dividing by a row height with a rounded reciprocal misses rows for 74 of 512 integer heights, so `emitFloorDivide` adds a remainder correction: 8 operations and 7 layers. A fractional input like a sub-pixel scroll offset needs quantizing before it can index anything.
- **Infinite candidates split the two constructions on purpose.** The instruction reads the selected value, while the dense sum turns into NaN. A circuit that moves between the two constructions changes behavior where a candidate can be infinite.
- **Proving bits needed declarations.** event-window's copy declares 13 source cells as bits and 2 one-hot groups, because a 0..1 source range could hold 0.5. For families of 2 to 4 members the savings are small: 446 to 414 live operations.
- **Once reads are cheap, the executor's per-evaluation costs dominate.** The 10,000-row list spends most of its 28 µs validating 30,001 source ranges for a 153-operation circuit.
- **The index gradient is 0 between integers.** A table of values trains, but learning where to read needs a soft read. `backward-difference` reproduces the relu one-hot's reference gradient, which is a finite difference, not a derivative.

### What stayed outside the circuit

- **Preparing tables.** pretext's segment widths and kinds were computed in JS once and written into the source table, along with the fit thresholds and paint ends derived from them, 10,000 row tops as prefix sums, photo aspect prefix sums, and the thumbnail constant tables.
- **Writing at a computed index.** The circuit can read `table[i]`, but writing `table[i] = value` into next-source cells still takes one select per cell, e.g. inserting a character at a caret.
- **Keys and strings.** A read needs an integer position, so a lookup by id resolves to a position in JS, or through integer equality in the circuit.
- **Measuring text, the scroll listener, and the DOM projection.** The demo writes `Math.round(scrollTop)` into a cell and copies outputs into styles.

## Open questions and next steps

- **Which form should the shared runtime take: the instruction, the recognition pass, or both?** The instruction has simpler semantics: infinite candidates are fine, nothing is built only to be removed, and no declared contract is involved. But it's a fourth runtime instruction, which lab/gather-lowering deliberately avoided. The recognition pass keeps three atoms but pays build time and needs the declared group.
- **A matching write.** A scatter for next-source tables, e.g. a text buffer edited at a caret, is the missing counterpart.
- **Constant-coefficient reads.** Recognizing sums like Photos' `sum focus[f] * constant(item, f)` and generating the constant table automatically would give IndirectOS the thumbnail savings without rewriting it.
- **Per-line widths.** pretext's per-start breakpoint rows (pretext.md 5.4) could read O(pieces) per line with index reads, instead of building an O(segments) one-hot per line.
- **Depth of sequential walks.** Pointer jumping is one associative formulation. Is there a formulation of line recovery with O(segments) work and log depth?
- **Code generation.** In generated JS or a shader, an index read is `values[base + stride * floor(index)]`, the same as a texel fetch with clamping. Measuring it in phase 1's code generation study would show whether reads stay cheap outside the executor.
- **Provenance through writeback.** A cell written back from a proven bit holds a bit on the next frame. Propagating that would replace most of event-window's declarations.
- **Validation cost.** Validating source ranges once at writeback, instead of on every evaluation, would stop large tables from setting the per-evaluation cost.
