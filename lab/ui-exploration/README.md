# How far the circuit approach goes for writing UI

**Start here.** To click through every demo from one page, run `bun lab/ui-exploration/serve-demos.ts` from the repo root and open http://127.0.0.1:4321/. For a first program, read [docs/tutorial.md](../../docs/tutorial.md), which walks through [template/](../../template/), a toggle switch checked against plain JavaScript. For short entries on the constructions, with current sizes and tests, read [docs/expressions.md](../../docs/expressions.md) (one familiar expression), [docs/patterns.md](../../docs/patterns.md) (loops) and [docs/behavior-choices.md](../../docs/behavior-choices.md) (choices that change what the user sees). For plain explanations of the concepts, with runnable examples checked against plain JavaScript, read [guide/README.md](guide/README.md). This README is the overnight synthesis, and each prototype's README has its full measurements.

This folder holds one night of exploration (September 12-13, 2026) around a single question: how far does HandwiredOS's approach take us for writing UI? That approach is an interactive UI written as one fixed numeric circuit of affine operations, ReLU-gated products, and exact bits, compiled into layers of sparse matmul, with JS only recording inputs and projecting outputs onto the DOM.

The work ran in rounds:

1. Seven readers mapped the runtime, HandwiredOS, the lab, Cheng's UI doctrine (chenguini's ui.md and demos, chenglou.github.io, nicer-hacker-news), pretext, and techniques from shaders, ML, and parallel algorithms. Their notes were in notes/, removed on September 16, 2026, and stay at the [exploration-2026-09 tag](https://github.com/chenglou/handwired/tree/exploration-2026-09/lab/ui-exploration/notes), where chenguini still has its earlier name, vibescript. Most of them also built and checked small circuits in scratch scripts.
2. Thirteen prototypes, each built by one agent, then checked by a second agent that tried to break its claims, then fixed. Every prototype has a README with measured results and sections on what fit well, what got awkward, and what stayed outside the circuit.
3. A third round after reading the talk "Repeatable breakthrough", plus two consolidation prototypes. See [Third round](#third-round).

During the exploration, nothing outside this folder changed: `numeric-ui-core.ts` stayed untouched, and prototypes that needed runtime changes changed a copy inside their own folder.

A new repo root file, `host-timing.ts` (moved into src/runtime/ on September 17, 2026), computes what JavaScript writes before each evaluation, e.g. frame durations, event times and the spring matrix. See decisions 1 to 3 in [the guide's decision record](guide/review-and-decisions.md#decisions-for-you). ## Short answer

Most of the UI logic the prototypes ported became a circuit: window management, fixed-step springs with catch-up, a virtualized list, drag-to-reorder cards, flick to a snap target, several pointer events per frame, keyboard focus and menus, Clay-style app layout, chenglou.github.io's 221-photo gallery, the nicer-hacker-news comment thread, a text field's editing model (insert and delete, caret and word movement, shift-selection, paste, wrapping at spaces and newlines, click to place the caret), and pretext's line walker itself, flowing text around a draggable window with a spring per word. Not ported: chenguini's scroll-anchor demo (keeping item identity when items are inserted), mobile-test-standalone, spring-comparison, the two global illumination demos, and hn.js's search, highlights, and selection.

Each prototype was checked against a reference, usually derived from the original code, and the decisions each README compared (focus, stacking, visibility, line membership, card order, and so on) matched on its traces. There are known exceptions, and all of them involve decisions that read drifting FP32 state: settle bits and "schedule another frame" bits sometimes flipped a frame earlier or later than the float64 original (lists, flick, [spring-bank](event-time/README.md#merged-from-spring-bank-september-16-2026)'s free-running bank), and far down the [gallery](instanced-items/README.md#merged-from-gallery-september-16-2026), pointers inside a 0.18 px band between index.ts's box edges and the circuit's box edges got a different hover and click. hn-thread counted decisions within 0.02 px of a threshold separately as ties.

Many loops that look sequential rewrite into counts of predicate bits, threshold tests, one-layer prefix sums, or matrix powers, a few to a few dozen layers deep: 1 layer for a prefix sum, 4 for tabulated text heights, 9 to 13 for layout's grow and shrink with min and max. Others stayed sequential scans whose depth grows with each iteration: walking lines (12 layers per line slot in text-editing), flex-wrap (about 4 layers per child), and presses within one frame (about 17 layers each in input). Where loops were rewritten, the cost moved into width: O(n²) comparisons, work written out once per item, and reading at computed indices.

Three features the runtime didn't have at the time account for most of that remaining cost. Since September 14, 2026, the runtime in src/runtime/ has the first one, the index read instruction ([execution-model.md](../../docs/execution-model.md#index-reads)), while the other two exist only in prototypes:

- **Reading at an integer index.** Today, reading `table[i]` needs an integer one-hot over the table's positions, 2 to 3 atoms per position. In text-walker at 1,023 segments, one-hots were 70-89% of the circuit (14-33% at 63 segments). [index-read](https://github.com/chenglou/handwired/tree/exploration-2026-09/lab/ui-exploration/index-read) added an `indexRead` instruction to a copy of the runtime: `values[index]` becomes 1 operation, and filling 24 DOM slots from a 10,000-row list becomes 153 operations ([lists](lists/README.md#merged-from-index-read-september-16-2026)).
- **An instance axis inside one UI.** The gallery writes its per-photo program out 221 times (48,411 operations). Written instead as per-photo programs plus a few reductions across photos (instanced-items), it is 233 operations per photo at any photo count, takes about 2 to 4 ms per frame at 10,000 photos on the CPU against about 43 ms for the duplicated circuit, and kept every decision equal to native index.ts at 10,000 synthetic photos.
- **An executor that doesn't interpret.** For HandwiredOS, interpretation is about 90% of the executor's CPU time, and generated JS runs a frame in 3.3 µs instead of 30 µs. Generated JS doesn't help wide circuits like the gallery and hn-thread, and its first frames are slow.

What stays outside is consistent across the prototypes: strings (segmentation, measurement, parsing, key names); platform side effects (`scrollTo`, `element.focus()`, `pushState`, `preventDefault`); DOM node lifetime and CSS strings; absolute clocks; preparing tables such as pretext's `prepare` and breakpoint tabulation, rerun whenever the text changes; changes to tree structure at runtime; and writing to a computed index.

pretext does translate, in two ways. Its layout results are step functions of the width with few steps, so heights, line counts, shrink-wrapped widths, and per-line cursors become comparisons against thresholds found at prepare time, 4 layers deep. And its fast-path walker (text, spaces, zero-width spaces) runs as circuit arithmetic over segment widths held in source cells, which is what lets text flow around moving geometry. Hard breaks, breakable long words, soft hyphens, letter spacing, and tabs also run in the circuit with a different width per line, but their thresholds are derived in JS, so editing a segment's width means rerunning that derivation.

The third round, after reading the talk, added a few things to that answer:

- Combining the wins makes UI richer but not cheaper. HandwiredOS with exact multi-event input and a paragraph flowing around the windows is 19,854 operations with a spring per word, and 18,027 since the word springs were removed on September 15, 2026, against 5,253 for the original.
- Writing the per-item program once and running it as instances is what keeps large collections affordable: the gallery stays 233 operations per photo at any count.
- In six of seven UIs, strict FP32 order mattered only at rounding points (boolean atoms, round chains, comparison differences): with stored order there and reordered, fused, or float64 sums everywhere else, no reference check changed. The gallery was the exception: its settle test compares a destination recomputed this frame with last frame's stored copy, which needs the same arithmetic in both frames. On the GPU, guards only at rounding points kept every decision exact on codegen's five instance workloads and 12 random circuits.
- Committing state only at event timestamps and at settle times derived from the committed state, with display frames that never write back, made committed tables identical in every bit at 10 to 240 fps and through 500 ms and 2 s stalls, for events delivered in timestamp order.
- input's compiled window circuit doubles as a simulator. 39 million user-frames of simulated users with authored hands mapped the tradeoffs of three behavior constants, a second run picked a slop and double-click distance per tremor level, and a 522-operation tremor estimate inside the circuit applies that table per user.
- Moving the string boundary down to code points, with line break rules as table reads, removed text-editing's grapheme vocabulary and cut line start mismatches with pretext from 8,806 to 215 of 41,820 layouts, including every mismatch in CJK ideographs, kana, and Hangul next to Latin words (2,023 before) and in Korean (1,620 before).
- Drawing per pixel removes the DOM slot router and the second text layout. Learning decision rules at the level of bits mostly didn't work; counting units beat 2-input gates, but no Tab rule was learned exactly from part of its cases.

## Rewrites that kept working

These constructions came up in prototype after prototype. They're the closest thing tonight produced to a vocabulary for writing UI in this style. [docs/expressions.md](../../docs/expressions.md) and [docs/patterns.md](../../docs/patterns.md) have a short entry for each, with its current size, when it's exact, and its test, and each prototype's README has its measurements.

- **Count instead of search when a predicate flips once.** The first visible row and the oldest sample in a pointer velocity window (lists), where a line ends (text-walker), the row under the pointer (hn-thread), the scroll anchor (the gallery in instanced-items), and where a click places the caret ([text-editing](code-points/README.md#merged-from-text-editing-september-16-2026)). See [`findIndex` when the test flips once along the items](../../docs/patterns.md#findindex-when-the-test-flips-once-along-the-items).
- **Prefix sums in one layer, with the same rounding as a loop.** Row tops and strip positions, e.g. the [gallery](instanced-items/README.md#merged-from-gallery-september-16-2026)'s photo strip in 9 layers, where the trace compiler's slice with the same outputs was 1,580 layers. See [running totals](../../docs/patterns.md#running-totals).
- **Fixed-step springs as matrix powers.** [spring-bank](event-time/README.md#merged-from-spring-bank-september-16-2026), reused by event-time and indirect-os-2, and merged into event-time on September 16, 2026: in spring-bank's copy of HandwiredOS, the circuit went from 5,253 operations and 192 layers to 3,580 and 137. See [a linear step repeated a runtime number of times](../../docs/patterns.md#a-linear-step-repeated-a-runtime-number-of-times).
- **Threshold counts instead of floor, sqrt, and division by runtime integers.** life-calendar's grid size (codegen), and the [gallery](instanced-items/README.md#merged-from-gallery-september-16-2026)'s column count, which is exact at widths such as 1,732 px, where the trace compiler's FP32 reciprocal picks one column too few. See the `Math.floor(x / step)` row of [expressions.md](../../docs/expressions.md#familiar-expressions).
- **Static structure becomes tables and wiring.** HN's ancestor walk and subtree gutters (hn-thread), and the gallery's row assignment per column count. See [a loop over data that rarely changes](../../docs/patterns.md#a-loop-over-data-that-rarely-changes).
- **Tabulate one runtime variable at prepare time.** Text heights, line counts, tight widths and balanced headings (text-tabulated), e.g. all 1,643 paragraphs of The Great Gatsby in 4 layers. See [a layout function of one runtime number](../../docs/patterns.md#a-layout-function-of-one-runtime-number).
- **Exact comparisons from rounding.** numeric-library's one-stage form keeps `d = a - b` as its own rounded wire and feeds `clamp01(0.5 + scale × d)` to the boolean atom, 4 operations, correct only while the largest possible difference is at most 2^45 times the smallest difference that has to be told apart from zero. Quantizing at the host boundary, e.g. scroll positions to 1/4 px, pointers to 1/64 px, and times to 1/64 ms relative to the frame, makes most decisions integer comparisons. The runtime's default in src/runtime/ is now `emitCompare`, see [Decision bits](../../docs/expressions.md#decision-bits).
- **A frame's queued pointer moves don't have to run one after another.** input handles every queued move at once from prefix counts, at about 46 operations per queue slot and no extra layers, while presses still run in order. See [a state machine over queued events](../../docs/patterns.md#a-state-machine-over-queued-events), whose "Don't use it when" covers this case.
- **Water filling for grow and shrink with min and max.** layout-tree's widths pass, at a constant depth from 2 to 64 children. See [growing and shrinking children with min and max](../../docs/patterns.md#growing-and-shrinking-children-with-min-and-max).
- **Ranks for runtime order, and an incremental layout when one item moves.** lists' drag-to-reorder cards. See [`items.sort(compare)`](../../docs/patterns.md#itemssortcompare).
- **Newton and Horner rows for division, sqrt, and trig.** numeric-library: a reciprocal over 1..16,384 in 50 operations, and sin and cos in 34. See the `x / y` and `Math.sqrt` rows of [expressions.md](../../docs/expressions.md#familiar-expressions).
- **Shared versus per-instance values, like uniforms versus per-fragment values in a shader.** codegen's instance axis, e.g. only 63 of life-calendar's 2,054 compiled rows run once per grid square. See [a loop over items that mixes per-item work with values carried to the next item](../../docs/patterns.md#a-loop-over-items-that-mixes-per-item-work-with-values-carried-to-the-next-item).

## Where it got awkward

**Reading at a computed index.** Every formulation that follows pointers or reads rows at a position pays for an integer one-hot. In text-walker, the formulation that allows a different width per line builds a one-hot of each line's start to read the thresholds after it; those one-hots are 89% of the circuit at 1,023 segments (361,890 operations), and an index read would bring it to about 40,825 (an estimate, not built). In hn-thread, routing visible rows into 48 DOM slots costs 25,616 operations, about as much as the rest of the thread's UI (28,340). index-read's instruction reads `candidates[floor(index)]` with no rounding: `values[index]` over 10,000 entries is 1 operation, and once pretext's next-start table exists (190,279 operations at 1,023 segments), recovering all 157 line starts costs 1,409 more operations, instead of 483,399 with the shared runtime's gather lowering ([text-walker](text-walker/README.md#merged-from-index-read-september-16-2026)).

**Work written out once per item.** The gallery's 221 photos are 48,411 operations, and springs are 64% of them. Generated JS doesn't help circuits this wide: the gallery took about 430-570 µs after 6,000 warm runs, against about 375-510 µs for the executor and 13 µs for native index.ts.

**O(n²) from runtime order.** In the direct drag-reorder port, the pairwise sections are 35% of the circuit at 50 cards and 68% at 200. Grow and shrink with min and max over runtime fit widths cost about 1.4 to 3.1 n² operations at 64 children (1.4 n² for grow alone, 2.2 n² for shrinking texts, 3.1 n² for both), while boxes with constant fit widths cost about 14 operations per child. Capacity routing costs O(items × slots).

**Depth follows dependency chains, plus the scans that weren't rewritten.** The gallery's 61 layers follow what the UI depends on: a click decides the focus, the focus decides the photo strip's positions and every photo's destination, the destinations decide the scroll anchor, the anchor decides the scroll adjustment, that adjustment shifts the springs, and the springs decide which photos are occluded. Line walks and flex-wrap are still sequential scans; parallel versions trade that depth for width, e.g. pointer jumping recovers a 1,023-segment paragraph's lines in 66 layers with index reads.

**Reading last frame's values.** Reading some values from the previous frame cuts depth a lot, at the cost of one frame of lag. With HandwiredOS's original springs, Photos reading last frame's content size and presence takes the circuit from 192 to 118 layers, and layout-tree's app shell goes from 115 to 83 layers when layout reads last frame's sidebar spring. The lag can be visible: with [spring-bank](event-time/README.md#merged-from-spring-bank-september-16-2026)'s springs, Photos reading last frame's window size gives 91 layers but was up to 86 px off during a maximize. spring-bank found a better option: Photos reads the window springs' positions right after this frame's steps, before the settle snap. Those positions depend only on source cells and the shared frame matrix, so they're computed early; HandwiredOS is still 91 layers, and Photos lags only during a live resize, by that frame's resize delta (6.6 px in the trace). Presence is still read from last frame, which would delay opacity by one frame when Photos opens or closes.

**FP32 details that bit more than once.**

- An exact integer bit such as `relu(v) - relu(v - 1)` can stop being exact inside an ordinary affine. The builder copies the bit's two ReLU terms into the sum that reads it, and when those ReLUs hold large values, the running FP32 sum rounds. In lists, fractional weights over ReLU values up to 8,192 made a reciprocal seed 233% wrong. In input, a 2^18 coefficient pushed partial sums past 2^24, and arrow navigation picked the wrong control. Keeping the bit as its own `roundAffine` wire fixes it.
- A path masked by a zero gate still computes, so an out-of-range value can become `0 × Infinity = NaN` and leak into state (lists).
- Absolute spring positions near 100,000 px can never settle in FP32, so the gallery stores each spring as a displacement plus its destination.
- The order in which wires are created changes FP32 results. An ordinary affine adds its terms in wire-number order, and wire numbers follow creation order, so moving a statement, e.g. computing the dock center before the window center, can round a fractional sum differently ([notation](https://github.com/chenglou/handwired/tree/exploration-2026-09/lab/ui-exploration/notation)). Update, September 17 to 18, 2026: the [term order probe](../status.md#term-order-probe-september-17-to-18-2026) found that the dock center case no longer reproduces in today's HandwiredOS. Both centers are sums of two addends, which round the same in either order, since each product is rounded before the one addition, and the select that reads them keeps the order written in its call. Of 6 statement moves the probe tried, the one that still changes values builds a thumbnail's gap × offset product before its base size × spread product in photo-gallery.ts, which reorders the three fractional addends of each thumbnail's `centerX`, and moves drawn thumbnails by at most 1.2e-4 px.
- A range declared on a wire after other operations already read it doesn't narrow those operations. Until September 15, 2026, HandwiredOS declared the spring timestep's range after the window springs existed, so they used 3-operation signed products; declaring it where it's computed saved 320 operations with bit-identical outputs ([notation](https://github.com/chenglou/handwired/tree/exploration-2026-09/lab/ui-exploration/notation), and indirect-os-2's [base.test.ts](https://github.com/chenglou/handwired/blob/exploration-2026-09/lab/ui-exploration/indirect-os-2/base.test.ts)).
- Range propagation ignores NaN: a product can get a finite declared range while holding `Infinity × 0 = NaN`. Gather lowering trusts that range and skips the unselected product, so when a source cell holds Infinity, the executor returns the selected value where the reference evaluator returns NaN (codegen).
- Apple's Metal shader compiler, reached through both wgpu and Dawn, fuses `a + b*c`, regroups sums, and folds `(x + K) - K`. Wrapping results in `max(x, lowest)`, with `lowest` loaded from a buffer, kept every workload bit-exact, which relies on the compiler not seeing through a runtime value. Other GPU backends weren't tested (codegen).

**Decisions on drifting continuous state.** A settle rule that compares drifting FP32 spring state against 0.01 can settle a spring one frame earlier or later than the float64 original. When that spring was the last one moving, one side restarts its animation clock and the other doesn't, so cards that start moving afterwards run up to a frame ahead or behind. In lists, 7 of 20 runs at 100 cards had such a flip, and positions then differed by up to 21 px (up to 173 px over 61 longer runs), while card order, z index, the dragged card, and the cursor still matched on every frame.

**Timing semantics.** In chenguini's demos, a new spring destination applies before the frame's catch-up steps, and those steps simulate time from before the event. So when a destination changes mid-animation, trajectories depend on frame rate: 157 px apart between 30 fps and 120 fps. [spring-bank](event-time/README.md#merged-from-spring-bank-september-16-2026)'s deferred retargeting makes this frame's steps still pull toward last frame's destination, with the new destination taking effect from this frame's time. That makes 10 fps to 120 fps and 500 ms and 2 s stalls agree within 0.003 px when every press lands on a frame time all compared rates render. When a press falls between frames, JS also has to evaluate the circuit once more at the press's timestamp, without rendering; with that, every rate agrees within 0.0051 px. The browser page doesn't do the extra evaluation yet.

**Fixed capacities.** Event slots per evaluation, text characters and line slots, DOM slots, and the FP32 integer budget for text-editing's glyph position keys (which add the field width once per newline, so a 1,024-character buffer only fits a 512 px wide field) are all fixed when the circuit is built. Line slots, windows, and run limits report overflow counts; JS splits event queues into more evaluations; the position key budget is checked when the circuit is built; and a full width table drops new graphemes.

**Executor speed.** Generated JS is fast only for narrow circuits split into functions of a few hundred rows, after seconds of warmup; the first frame costs about 5 ms. Once the interpreter is gone, per-frame JS validation dominates: a frame loop with generated JS takes 50 µs with HandwiredOS's hand-written validation against 3.6 µs without. notation's validators, derived from declarations, cost about 1 µs per frame for all checks (0.3 µs for the source table alone) and check somewhat different rules; pairing them with generated JS wasn't measured.

## pretext

**Tabulated.** For a prepared paragraph, every layout result is a step function of the width. A prepare step bisects over FP32 widths, and the circuit compares one runtime width against the thresholds with a 4-atom comparison that's exact at every FP32 width in 0..8,192, for thresholds of 0 or in 2^-10..8,192. No feature-specific code was needed: soft hyphens, emergency breaks, tabs, letter spacing, CJK, keep-all, and pre-wrap all matched pretext's own test cases. A Notes window with a springing width and 10 reflowing blocks (paragraphs, shrink-wrapped chat bubbles, a balanced heading) is 2,030 operations. Painting every line of a very long paragraph is expensive (a 4,096-word paragraph needs 153,549 weights for all line cursors), and anything depending on a second runtime variable, such as per-line widths around an obstacle, needs the walker itself.

**The walker as arithmetic.** For a line starting at segment s, the bits "segments s through j fit in `maxWidth + lineFitEpsilon`" read 1...1 0...0, so where the line ends is a count. The next start, the painted width, and each word's line index and x come from the same bits. Five ways of recovering lines matched pretext at 63 and 255 segments over 1,281 widths, and four of them at 1,023 segments (pointer jumping was only built up to 255 segments and only compared on line count and widest line). The other features (hard breaks, breakable long words with grapheme units, soft hyphens, letter spacing, tabs) matched too, but for those, JS restates pretext's walker for every start position and writes each start's thresholds into source cells. The circuit compares those thresholds with each line's width, so per-line widths still change at runtime, while editing a segment's width means recomputing the thresholds in JS.

**Does a paragraph ever get more lines when it gets wider?** Over 2,400 random plain texts across three engine profiles, with and without kerning, no: the line count never went up as the width grew, and no line start moved backward. Rich inline content is different, and this may be worth a look in pretext itself. In 71 of 80 random flows per engine profile, there's a band: a run of widths that lays out worse than the width just below it, with more lines or a line starting earlier. Most bands are exactly one `lineFitEpsilon` wide. In the smallest example, in the Blink profile, a 12 px "q" followed by a 20 px "-w", the item's own line walker fits "-w" within `availableWidth + lineFitEpsilon`, but `stepRichInlineLine` then checks `lineWidthContribution > remainingWidth` without the epsilon and wraps before the item. Bands of 1 px or more, up to 10.4 px, all involve soft hyphens. See [text-tabulated](text-tabulated/README.md).

**Fonts.** Headless checks used a fake canvas: widths on a grid of 1/64 of the font size, plus a non-dyadic run in text-tabulated (0 wrong decisions, widths drifting up to 1.8e-4 px). In Chrome with real fonts, text-walker's demo counted 0 mismatches against pretext over 236 states, and text-tabulated's demo counted 0 frames with a wrong line count, tight width, cursor, or line text over 2,473 frames.

- **Landed in the runtime, not in HandwiredOS.** HandwiredOS's springs integrate four substeps of the frame duration with a 32 ms clamp, so trajectories depend on frame rate and a stall loses time. [spring-bank](event-time/README.md#merged-from-spring-bank-september-16-2026)'s fixed-step bank is cheaper (3,580 against 5,253 operations in its HandwiredOS copy). It's frame-rate independent with deferred retargeting, and when presses fall between frames, with one extra evaluation at each press's timestamp. - Declaring the spring timestep nonnegative where it's computed saves 320 operations with bit-identical outputs.

Replacing HandwiredOS's select chain with it wasn't tried.

Since September 15, 2026, `assumeRange` and `assumeGrid` throw in that case ([execution-model.md](../../docs/execution-model.md#declarations)). For integer bits inside large sums, input notes that the builder can't see locally how large a bit's ReLUs get, so a check would have to rely on declared ranges.
- NaN-aware range propagation, so gather lowering stays sound when a source cell holds Infinity.
- **Landed.** Marking rounding points in the builder. ## Third round

After the first two rounds, three agents read the talk "Repeatable breakthrough" against tonight's results, each through one lens: a smaller unit of composition, homogeneity enabling uniform direction, and premature compression. Their notes are [notes/talk-smaller-unit.md](https://github.com/chenglou/handwired/blob/exploration-2026-09/lab/ui-exploration/notes/talk-smaller-unit.md), [notes/talk-uniform-direction.md](https://github.com/chenglou/handwired/blob/exploration-2026-09/lab/ui-exploration/notes/talk-uniform-direction.md), and [notes/talk-premature-compression.md](https://github.com/chenglou/handwired/blob/exploration-2026-09/lab/ui-exploration/notes/talk-premature-compression.md), at the exploration-2026-09 tag since the notes were removed on September 16, 2026. Each ran small scratch experiments before proposing anything.

What they noticed:

- The runtime's unit is already small, a wire computed by one atom, but most prototypes still built UI from larger units, and the biggest costs came from fitting those units into a fixed circuit: DOM slots (hn-thread's slot router is 25,616 operations), paragraphs walked line by line (at 1,023 segments, integer one-hots are 89% of text-walker's circuit, and each line adds about 8.75 layers), the frame as the only moment state changes (divergence between frame rates when presses fall between frames), and per-item code copied once per item (the gallery). Where the unit was already small and repeated, the approach was cheapest: one animated number is 4 products against a frame matrix that all springs share, a queued pointer move is about 46 operations, and one pixel of HandwiredOS's press map is 458 operations.
- Several times, working one level below the usual unit gave a capability the unit couldn't express. Going below pretext's `layout(width)` call to the line walker's comparisons gave a different width per line, e.g. text flowing around a dragged window. Going below the frame to the 4 ms spring step gave frame-rate independence, with the timing conditions described above. Going below the widget to the pixel gave a map of which window receives a press at each of 1,024,000 pixels, in about 2 ms on the GPU through Dawn once the pixel coordinates are uploaded. Going below one-hot bits to a floor inside the executor gave reads that cost 1 operation.
- Because every compiled UI is built from the same three atoms over one source table, the lens suggests four operations that work on any of them with no code per feature: evaluate it over many instances, differentiate outputs with respect to source cells, instrument its decisions, and edit behavior constants that live in cells. Scratch runs tried the first two. One pushed 65,536 simulated users through 300 frames each of lab/event-window's circuit at about 250 ns per user-frame, with 0 mismatches for the 16 users also run through the oracle, and produced a tradeoff table for one behavior constant, the drag slop: the authored 4 px slop cancels 17% of clicks for users with 2 px of tremor, and no single slop served both steady and shaky hands. The other used candidate-gallery.ts, which scores three candidate layouts and shows the best one. For a request to make the hero image 60 px wider, one backward pass (3 to 4 µs) and one step changed two design constants held in source cells, the gap (14 to 13.56 px) and the rail maximum (280 to 221.3 px). But at 405 of 1,377 scanned viewports the top layouts tie, because each score is clamped at 1; there the gradient is 0 and a search has to take over. Instrumenting decisions and patching cells remain proposals, and patching only reaches constants that aren't folded into weights.
- Exactness may only be needed at rounding points. In a scratch interpreter over one scripted 240-frame HandwiredOS session, reversing, balancing, or fusing every sum, or running in float64, flipped 0 of 64 booleans and 0 of 48 discrete state cells. Window positions and sizes drifted by at most 0.0022 px. The larger differences the scratch run reported as px, up to 0.59 when each mode ran on the reference's source tables and 1.8 when each mode drove its own state, with one 13.9 spike under reversed term order, turned out to be the windows' stacking output in z-index units ([exactness-budget](codegen/README.md#merged-from-exactness-budget-september-16-2026)). Over that session, 2,039 of HandwiredOS's 5,253 live values were exact bits in every frame, and 842 more were integers below 2^15.
- Bits as learned logic gates didn't work out of the box. A scratch differentiable logic gate network learned the Tab rule exactly for 2 controls, but reached at most 53 of 64 cases for 3 controls, 35 of 48 held-out cases for 4, and 458 of 896 cases for 6, while a counting construction from input's keyboard code handles 6 controls exactly in 127 operations. Many exact decisions tonight were a count followed by a threshold, e.g. Tab with disabled controls, the segment where a line overflows, and the row under the pointer, which suggests the counting bit, rather than the 2-input gate, may be the natural unit of learned behavior in this runtime.

Assumptions they flagged as possibly premature: the frame as the moment state changes; hit regions belonging to elements; the paragraph or message as the unit of text; outputs describing a whole capacity instead of what has arrived; per-item code copied per item; FP32 as the only numeric floor; the DOM as the output; strings and a grapheme vocabulary settled in JS; the index read as a special instruction (it's hard attention whose keys are positions); and circuits written by hand, when text-tabulated's black-box sampling absorbed every pretext feature with no feature-specific code.

Prototypes built from these proposals, and the two consolidation prototypes that ran alongside them, one line each. [guide/sections/talk.md](guide/sections/talk.md) explains each one plainly, and each folder's README has its measurements:

- [streaming-words](streaming-words/): a streamed chat reply where every word springs, and a bubble is a reduction over words. Every arrived word got pretext's line and x in all 7,419 streamed states checked, and stopping a reply writes back 1 cell, or 2 when the press lands inside a word ([explanation](guide/sections/talk.md#streaming-words-the-word-instead-of-the-chat-bubble)).
- [event-time](event-time/): state committed per event, display frames that never write back, and all of HandwiredOS predicted until the next event as keyframes. Committed tables differed in 0 bits between 240 fps and 10, 30, 60 and 120 fps, and through 500 ms and 2 s stalls ([explanation](guide/sections/talk.md#event-time-the-event-and-the-4-ms-step-instead-of-the-frame)).
- [pixel-output](pixel-output/): the HN thread drawn per pixel, with no DOM slot router. The router's 25,616 operations disappear, and a pixel with real text costs 455 rows ([explanation](guide/sections/talk.md#pixel-output-the-pixel-instead-of-the-dom-element)).
- [code-points](code-points/): code points in cells, with advances and line break rules read from tables inside the circuit. Line start mismatches with pretext went from 8,806 to 215 of 41,820 layouts, with the pair table and CJK runs kept whole ([explanation](guide/sections/talk.md#code-points-unicodes-numbers-instead-of-a-vocabulary-that-javascript-builds)).
- [learned-bits](learned-bits/): learning UI decision rules as 2-input gates versus counting units, with exhaustive certification. Neither unit type learned any task exactly at base settings, and counting units got more cases right than gates on 7 of 8 tasks ([explanation](guide/sections/talk.md#learned-bits-learned-bits-instead-of-written-rules)).
- [user-population](user-population/): simulated users running input's window circuit as instances, to choose behavior constants. Over 39,321,600 user-frames, the best drag slop per tremor level was 3, 4, 7 and 10 px, for simulated users whose hands were authored ([explanation](guide/sections/talk.md#user-population-a-city-of-simulated-users)).
- [drag-knobs](drag-knobs/): dragging an output edge of layout-tree's app shell moves design constants held in source cells through a backward pass, with search when a decision blocks the gradient. Over 500 scripted drags, one gradient step solved 63.6% of moving frames ([explanation](guide/sections/talk.md#drag-knobs-dragging-an-edge-moves-the-design-numbers)).
- [exactness-budget](codegen/README.md#merged-from-exactness-budget-september-16-2026), merged into codegen on September 16, 2026: perturbed executors over seven UIs, and GPU shaders guarded only at rounding points. Reordering, balancing and fusing sums changed one reference check across all the UIs, a gallery settle bit a frame late, while float64 broke every UI that rounds on purpose ([explanation](guide/sections/talk.md#exactness-budget-which-exactness-a-ui-needs)).
- [retiming](https://github.com/chenglou/handwired/tree/exploration-2026-09/lab/ui-exploration/retiming), removed on September 16, 2026: one-frame delays chosen by search against a visible-error budget. None of tonight's hand-chosen cuts fits a 1 px budget, and a search on one trace overfits ([explanation](guide/sections/talk.md#retiming-letting-some-values-be-one-frame-old)).
- [indirect-os-2](https://github.com/chenglou/handwired/tree/exploration-2026-09/lab/ui-exploration/indirect-os-2), removed on September 16, 2026, after root HandwiredOS took its Notes flow: HandwiredOS rebuilt with the notation, the spring bank, the event queue, generated JS, and a Notes window whose text flows around the other windows. The whole program was 19,854 operations and 343 layers with a spring per word, and is 18,027 and 337 since the word springs were removed on September 15, 2026, against the original's 5,253 and 192: richer and still exact, but not cheaper ([explanation](guide/sections/talk.md#indirect-os-2-do-the-improvements-add-up)). [input's README](input/README.md#merged-from-indirect-os-2-september-16-2026) keeps its event queue, and [codegen's](codegen/README.md#merged-from-indirect-os-2-september-16-2026) its tiered execution.
- [instanced-items](instanced-items/): per-item programs written once and run as instances, with reductions between stages, applied to the gallery. 233 operations per photo at any photo count, and 0 decision mismatches against native index.ts at 221, 1,000 and 10,000 photos, the last with Brent-Kung prefix sums ([explanation](guide/sections/talk.md#instanced-items-one-program-per-item-like-a-shader-per-pixel)).

Proposed but not built tonight: routing presses by reading a per-pixel owner map instead of hit-testing in the scalar circuit; a design atlas of design variants × viewports as instances, searching for ties and reflow jumps; decision margins as one uniform output that says where a circuit is fragile, to direct reference checks; behavior edits as cell patches an agent can make without recompiling, and what lifting the remaining constants into cells costs; candidate futures (several next source tables evaluated as instances, one committed); and field morphs, where every pixel's signed distance springs toward the next UI state.
