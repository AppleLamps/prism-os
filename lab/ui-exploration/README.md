# How far the circuit approach goes for writing UI

**Start here.** To click through every demo from one page, run `bun lab/ui-exploration/serve-demos.ts` from the repo root and open http://127.0.0.1:4321/. For plain explanations of the concepts, with runnable examples checked against plain JavaScript, read [guide/README.md](guide/README.md). This README is the overnight synthesis, with every prototype's numbers.

This folder holds one night of exploration (September 12-13, 2026) around a single question: how far does IndirectOS's approach take us for writing UI? That approach is an interactive UI written as one fixed numeric circuit of affine operations, ReLU-gated products, and exact bits, compiled into layers of sparse matmul, with JS only recording inputs and projecting outputs onto the DOM.

The work ran in rounds:

1. Seven readers mapped the runtime, IndirectOS, the lab, Cheng's UI doctrine (vibescript's ui.md and demos, chenglou.github.io, nicer-hacker-news), pretext, and techniques from shaders, ML, and parallel algorithms. Their notes are in [notes/](notes/). Most of them also built and checked small circuits in scratch scripts.
2. Thirteen prototypes, each built by one agent, then checked by a second agent that tried to break its claims, then fixed. Every prototype has a README with measured results and sections on what fit well, what got awkward, and what stayed outside the circuit.
3. A third round after reading the talk "Repeatable breakthrough", plus two consolidation prototypes. See [Third round](#third-round).

Nothing outside this folder was changed. `numeric-ui-core.ts` is untouched; prototypes that needed runtime changes changed a copy inside their own folder.

Update, September 14, 2026: the repo root `numeric-ui-core.ts` has since gained an index read instruction (`indexRead`, `indexReadAffine`), the comparison helper `emitCompare` with declared grids and rounding point records (`assumeGrid`, `markRoundingPoint`, `roundingPoints`), and springs whose step matrix JavaScript writes into source cells (`emitApplySpringMatrix`, `emitAnimatedObject`). A new repo root file, `host-timing.ts`, computes what JavaScript writes before each evaluation, e.g. frame durations, event times and the spring matrix. See decisions 1 to 3 in [the guide's decision record](guide/review-and-decisions.md#decisions-for-you). The prototypes below were built on the root runtime as it was at commit a915dcb, or on copies inside their folders.

## Short answer

Most of the UI logic the prototypes ported became a circuit: window management, fixed-step springs with catch-up, a virtualized list, drag-to-reorder cards, flick to a snap target, several pointer events per frame, keyboard focus and menus, Clay-style app layout, chenglou.github.io's 221-photo gallery, the nicer-hacker-news comment thread, a text field's editing model (insert and delete, caret and word movement, shift-selection, paste, wrapping at spaces and newlines, click to place the caret), and pretext's line walker itself, flowing text around a draggable window with a spring per word. Not ported: vibescript's scroll-anchor demo (keeping item identity when items are inserted), mobile-test-standalone, spring-comparison, the two global illumination demos, and hn.js's search, highlights, and selection.

Each prototype was checked against a reference, usually derived from the original code, and the decisions each README compared (focus, stacking, visibility, line membership, card order, and so on) matched on its traces. There are known exceptions, and all of them involve decisions that read drifting FP32 state: settle bits and "schedule another frame" bits sometimes flipped a frame earlier or later than the float64 original (lists, flick, spring-bank's free-running bank), and far down the gallery, pointers inside a 0.18 px band between index.ts's box edges and the circuit's box edges got a different hover and click. hn-thread counted decisions within 0.02 px of a threshold separately as ties.

Many loops that look sequential rewrite into counts of predicate bits, threshold tests, one-layer prefix sums, or matrix powers, a few to a few dozen layers deep: 1 layer for a prefix sum, 4 for tabulated text heights, 9 to 13 for layout's grow and shrink with min and max. Others stayed sequential scans whose depth grows with each iteration: walking lines (12 layers per line slot in text-editing), flex-wrap (about 4 layers per child), and presses within one frame (about 17 layers each in input). Where loops were rewritten, the cost moved into width: O(n²) comparisons, work written out once per item, and reading at computed indices.

Three features the runtime doesn't have yet account for most of that remaining cost:

- **Reading at an integer index.** Today, reading `table[i]` needs an integer one-hot over the table's positions, 2 to 3 atoms per position. In text-walker at 1,023 segments, one-hots were 70-89% of the circuit (14-33% at 63 segments). index-read added an `indexRead` instruction to a copy of the runtime: `values[index]` becomes 1 operation, and filling 24 DOM slots from a 10,000-row list becomes 153 operations.
- **An instance axis inside one UI.** The gallery writes its per-photo program out 221 times (48,411 operations). Written instead as per-photo programs plus a few reductions across photos (instanced-items), it is 233 operations per photo at any photo count, takes about 2 to 4 ms per frame at 10,000 photos on the CPU against about 43 ms for the duplicated circuit, and kept every decision equal to native index.ts at 10,000 synthetic photos.
- **An executor that doesn't interpret.** For IndirectOS, interpretation is about 90% of the executor's CPU time, and generated JS runs a frame in 3.3 µs instead of 30 µs. Generated JS doesn't help wide circuits like the gallery and hn-thread, and its first frames are slow.

What stays outside is consistent across the prototypes: strings (segmentation, measurement, parsing, key names); platform side effects (`scrollTo`, `element.focus()`, `pushState`, `preventDefault`); DOM node lifetime and CSS strings; absolute clocks; preparing tables such as pretext's `prepare` and breakpoint tabulation, rerun whenever the text changes; changes to tree structure at runtime; and writing to a computed index.

pretext does translate, in two ways. Its layout results are step functions of the width with few steps, so heights, line counts, shrink-wrapped widths, and per-line cursors become comparisons against thresholds found at prepare time, 4 layers deep. And its fast-path walker (text, spaces, zero-width spaces) runs as circuit arithmetic over segment widths held in source cells, which is what lets text flow around moving geometry. Hard breaks, breakable long words, soft hyphens, letter spacing, and tabs also run in the circuit with a different width per line, but their thresholds are derived in JS, so editing a segment's width means rerunning that derivation.

The third round, after reading the talk, added a few things to that answer:

- Combining the wins makes UI richer but not cheaper. IndirectOS with exact multi-event input and a paragraph flowing around the windows is 19,854 operations, against 5,253 for the original.
- Writing the per-item program once and running it as instances is what keeps large collections affordable: the gallery stays 233 operations per photo at any count.
- In six of seven UIs, strict FP32 order mattered only at rounding points (boolean atoms, round chains, comparison differences): with stored order there and reordered, fused, or float64 sums everywhere else, no reference check changed. The gallery was the exception: its settle test compares a destination recomputed this frame with last frame's stored copy, which needs the same arithmetic in both frames. On the GPU, guards only at rounding points kept every decision exact on codegen's five instance workloads and 12 random circuits.
- Committing state only at event timestamps and at settle times derived from the committed state, with display frames that never write back, made committed tables identical in every bit at 10 to 240 fps and through 500 ms and 2 s stalls, for events delivered in timestamp order.
- input's compiled window circuit doubles as a simulator. 39 million user-frames of simulated users with authored hands mapped the tradeoffs of three behavior constants, a second run picked a slop and double-click distance per tremor level, and a 522-operation tremor estimate inside the circuit applies that table per user.
- Moving the string boundary down to code points, with line break rules as table reads, removed text-editing's grapheme vocabulary and cut line start mismatches with pretext from 8,806 to 215 of 41,820 layouts, including every mismatch in CJK ideographs, kana, and Hangul next to Latin words (2,023 before) and in Korean (1,620 before).
- Drawing per pixel removes the DOM slot router and the second text layout. Learning decision rules at the level of bits mostly didn't work; counting units beat 2-input gates, but no Tab rule was learned exactly from part of its cases.

## Rewrites that kept working

These constructions came up in prototype after prototype. They're the closest thing tonight produced to a vocabulary for writing UI in this style.

- **Count instead of search when a predicate flips once.** If rows are sorted, or widths are nonnegative, a predicate evaluated along the index reads 1...1 0...0, so the first match is the count of ones, and the answer's one-hot is the difference of neighboring bits, with no products. This found the first visible row (lists), where a line ends (text-walker), the row under the pointer (hn-thread), the scroll anchor (gallery), the oldest sample in a pointer velocity window (lists), and where a click places the caret (text-editing).
- **Prefix sums in one layer, with the same rounding as a loop.** Each output is one wide `roundAffine` sum whose terms are in the same order as the sequential loop, e.g. `rowTop[5] = height[0] + ... + height[4]`. That reproduces the loop's FP32 rounding exactly in 1 layer, for n²/2 stored weights. A Brent-Kung network stores far fewer weights at the cost of a few more layers. The gallery's hand-written photo strip is 9 layers this way (21 with Brent-Kung), where the trace compiler's slice with the same outputs was 1,580 layers, mostly from sequential sums and 25-layer comparison cascades.
- **Fixed-step springs as matrix powers.** With constant stiffness and damping, one 4 ms step is a 2x2 matrix, so a frame's N steps are a product of constant powers selected by the bits of N. Every spring with the same stiffness and damping reads that one matrix with 4 products, and one exact settle bit covers all the springs of one animated object, e.g. a window's 5 springs. In spring-bank's copy of IndirectOS, the circuit went from 5,253 operations and 192 layers to 3,580 and 137.
- **Threshold counts instead of floor, sqrt, and division by runtime integers.** vibescript's life-calendar sizes its grid with sqrt, floor, and division; the same result is a count of 141 linear threshold tests (codegen). The gallery's column count, written as threshold tests, is exact at widths such as 1,732 px, where the trace compiler's FP32 reciprocal picks one column too few.
- **Static structure becomes tables and wiring.** HN's ancestor walk is a table prepared ahead of time, read through two one-hots, and a subtree's gutter bottom is a direct wire to the top of the row after the subtree. The gallery's row assignment is fixed per column count.
- **Tabulate one runtime variable at prepare time.** Anything that depends monotonically on one width (text heights, line counts, tight widths, balanced headings) becomes `base + Σ delta × [width >= threshold]`. Heights for all 1,643 paragraphs of The Great Gatsby cost 21,549 operations in 4 layers (text-tabulated).
- **Exact comparisons from rounding.** An exact `[a >= b]` costs 4 operations: keep `d = a - b` as its own rounded wire, scale it by a power of two, and feed `clamp01(0.5 + scale × d)` to the boolean atom. One such stage decides correctly as long as the largest possible difference is at most 2^45 times the smallest difference that has to be told apart from zero; for example, pixel values in 0..16,384 compare exactly whenever they differ by at least 2^-30 px (numeric-library). Integer decisions use `relu(v - t + 1) - relu(v - t)`. Quantizing at the host boundary, e.g. scroll positions to 1/4 px, pointers to 1/64 px, and times to 1/64 ms relative to the frame, makes most decisions integer comparisons.
- **A frame's queued pointer moves don't have to run one after another.** When a move only affects later events through a latch (e.g. the press point), a count, or an OR (e.g. "moved past the drag slop since the press"), every move in the queue can be handled at once from prefix counts, at about 46 operations per queue slot and no extra layers. Only presses still run in order, because a press hit-tests geometry that an earlier release may have changed, e.g. a window dropped at a new position earlier in the same frame (input).
- **Water filling for grow and shrink with min and max.** Clay distributes leftover space with a loop that takes up to 226 rounds at 64 children. Evaluating the total at each child's own clamp points instead gives the clamp bits at a constant depth in the widths pass, from 2 to 64 children: 9 layers for boxes with constant fit widths, 11 to 13 when fit widths are runtime values. When FP32 flips a bit near a tie, sizes change continuously, so the flip shows up as drift rather than a jump (layout-tree).
- **Ranks for runtime order, and an incremental layout when one item moves.** Counting how many cards a dragged card has passed reproduces draggable-cards' swap loops exactly. When a drag moves only one card, an O(n) update replaces n²/2 comparisons, but it relies on the previous frame's layout (lists).
- **Newton and Horner rows for division, sqrt, and trig.** With the gate folded into the ReGLU row, a Newton step is 2 operations: a reciprocal over 1..16,384 costs 50 operations, and sin and cos cost 34 (numeric-library).
- **Shared versus per-instance values, like uniforms versus per-fragment values in a shader.** A value is per-instance only when it reads a per-instance source cell, directly or indirectly, so the shared part is split out and computed once automatically. For example, life-calendar has 27,393 grid squares, and only 63 of its 2,054 compiled rows run once per square; the other 1,991 run once for the whole grid (codegen).

## Where it got awkward

**Reading at a computed index.** Every formulation that follows pointers or reads rows at a position pays for an integer one-hot. In text-walker, the formulation that allows a different width per line builds a one-hot of each line's start to read the thresholds after it; those one-hots are 89% of the circuit at 1,023 segments (361,890 operations), and an index read would bring it to about 40,825 (an estimate, not built). In hn-thread, routing visible rows into 48 DOM slots costs 25,616 operations, about as much as the rest of the thread's UI (28,340). index-read's instruction reads `candidates[floor(index)]` with no rounding: `values[index]` over 10,000 entries is 1 operation, and once pretext's next-start table exists (190,279 operations at 1,023 segments), recovering all 157 line starts costs 1,409 more operations, instead of 483,399 with the shared runtime's gather lowering.

**Work written out once per item.** The gallery's 221 photos are 48,411 operations, and springs are 64% of them. Generated JS doesn't help circuits this wide: the gallery took about 430-570 µs after 6,000 warm runs, against about 375-510 µs for the executor and 13 µs for native index.ts.

**O(n²) from runtime order.** In the direct drag-reorder port, the pairwise sections are 35% of the circuit at 50 cards and 68% at 200. Grow and shrink with min and max over runtime fit widths cost about 1.4 to 3.1 n² operations at 64 children (1.4 n² for grow alone, 2.2 n² for shrinking texts, 3.1 n² for both), while boxes with constant fit widths cost about 14 operations per child. Capacity routing costs O(items × slots).

**Depth follows dependency chains, plus the scans that weren't rewritten.** The gallery's 61 layers follow what the UI depends on: a click decides the focus, the focus decides the photo strip's positions and every photo's destination, the destinations decide the scroll anchor, the anchor decides the scroll adjustment, that adjustment shifts the springs, and the springs decide which photos are occluded. Line walks and flex-wrap are still sequential scans; parallel versions trade that depth for width, e.g. pointer jumping recovers a 1,023-segment paragraph's lines in 66 layers with index reads.

**Reading last frame's values.** Reading some values from the previous frame cuts depth a lot, at the cost of one frame of lag. With IndirectOS's original springs, Photos reading last frame's content size and presence takes the circuit from 192 to 118 layers, and layout-tree's app shell goes from 115 to 83 layers when layout reads last frame's sidebar spring. The lag can be visible: with spring-bank's springs, Photos reading last frame's window size gives 91 layers but was up to 86 px off during a maximize. spring-bank found a better option: Photos reads the window springs' positions right after this frame's steps, before the settle snap. Those positions depend only on source cells and the shared frame matrix, so they're computed early; IndirectOS is still 91 layers, and Photos lags only during a live resize, by that frame's resize delta (6.6 px in the trace). Presence is still read from last frame, which would delay opacity by one frame when Photos opens or closes.

**FP32 details that bit more than once.**

- An exact integer bit such as `relu(v) - relu(v - 1)` can stop being exact inside an ordinary affine. The builder copies the bit's two ReLU terms into the sum that reads it, and when those ReLUs hold large values, the running FP32 sum rounds. In lists, fractional weights over ReLU values up to 8,192 made a reciprocal seed 233% wrong. In input, a 2^18 coefficient pushed partial sums past 2^24, and arrow navigation picked the wrong control. Keeping the bit as its own `roundAffine` wire fixes it.
- A path masked by a zero gate still computes, so an out-of-range value can become `0 × Infinity = NaN` and leak into state (lists).
- Absolute spring positions near 100,000 px can never settle in FP32, so the gallery stores each spring as a displacement plus its destination.
- The order in which wires are created changes FP32 results. An ordinary affine adds its terms in wire-number order, and wire numbers follow creation order, so moving a statement, e.g. computing the dock center before the window center, can round a fractional sum differently (notation).
- A range declared on a wire after other operations already read it doesn't narrow those operations. IndirectOS declares the spring timestep's range after the window springs exist, so they use 3-operation signed products; declaring it where it's computed saves 320 operations with bit-identical outputs (notation).
- Range propagation ignores NaN: a product can get a finite declared range while holding `Infinity × 0 = NaN`. Gather lowering trusts that range and skips the unselected product, so when a source cell holds Infinity, the executor returns the selected value where the reference evaluator returns NaN (codegen).
- Apple's Metal shader compiler, reached through both wgpu and Dawn, fuses `a + b*c`, regroups sums, and folds `(x + K) - K`. Wrapping results in `max(x, lowest)`, with `lowest` loaded from a buffer, kept every workload bit-exact, which relies on the compiler not seeing through a runtime value. Other GPU backends weren't tested (codegen).

**Decisions on drifting continuous state.** A settle rule that compares drifting FP32 spring state against 0.01 can settle a spring one frame earlier or later than the float64 original. When that spring was the last one moving, one side restarts its animation clock and the other doesn't, so cards that start moving afterwards run up to a frame ahead or behind. In lists, 7 of 20 runs at 100 cards had such a flip, and positions then differed by up to 21 px (up to 173 px over 61 longer runs), while card order, z index, the dragged card, and the cursor still matched on every frame.

**Timing semantics.** In vibescript's demos, a new spring destination applies before the frame's catch-up steps, and those steps simulate time from before the event. So when a destination changes mid-animation, trajectories depend on frame rate: 157 px apart between 30 fps and 120 fps. spring-bank's deferred retargeting makes this frame's steps still pull toward last frame's destination, with the new destination taking effect from this frame's time. That makes 10 fps to 120 fps and 500 ms and 2 s stalls agree within 0.003 px when every press lands on a frame time all compared rates render. When a press falls between frames, JS also has to evaluate the circuit once more at the press's timestamp, without rendering; with that, every rate agrees within 0.0051 px. The browser page doesn't do the extra evaluation yet.

**Fixed capacities.** Event slots per evaluation, text characters and line slots, DOM slots, and the FP32 integer budget for text-editing's glyph position keys (which add the field width once per newline, so a 1,024-character buffer only fits a 512 px wide field) are all fixed when the circuit is built. Line slots, windows, and run limits report overflow counts; JS splits event queues into more evaluations; the position key budget is checked when the circuit is built; and a full width table drops new graphemes.

**Executor speed.** Generated JS is fast only for narrow circuits split into functions of a few hundred rows, after seconds of warmup; the first frame costs about 5 ms. Once the interpreter is gone, per-frame JS validation dominates: a frame loop with generated JS takes 50 µs with IndirectOS's hand-written validation against 3.6 µs without. notation's validators, derived from declarations, cost about 1 µs per frame for all checks (0.3 µs for the source table alone) and check somewhat different rules; pairing them with generated JS wasn't measured.

## pretext

**Tabulated.** For a prepared paragraph, every layout result is a step function of the width. A prepare step bisects over FP32 widths, and the circuit compares one runtime width against the thresholds with a 4-atom comparison that's exact at every FP32 width in 0..8,192, for thresholds of 0 or in 2^-10..8,192. No feature-specific code was needed: soft hyphens, emergency breaks, tabs, letter spacing, CJK, keep-all, and pre-wrap all matched pretext's own test cases. A Notes window with a springing width and 10 reflowing blocks (paragraphs, shrink-wrapped chat bubbles, a balanced heading) is 2,030 operations. Painting every line of a very long paragraph is expensive (a 4,096-word paragraph needs 153,549 weights for all line cursors), and anything depending on a second runtime variable, such as per-line widths around an obstacle, needs the walker itself.

**The walker as arithmetic.** For a line starting at segment s, the bits "segments s through j fit in `maxWidth + lineFitEpsilon`" read 1...1 0...0, so where the line ends is a count. The next start, the painted width, and each word's line index and x come from the same bits. Five ways of recovering lines matched pretext at 63 and 255 segments over 1,281 widths, and four of them at 1,023 segments (pointer jumping was only built up to 255 segments and only compared on line count and widest line). The other features (hard breaks, breakable long words with grapheme units, soft hyphens, letter spacing, tabs) matched too, but for those, JS restates pretext's walker for every start position and writes each start's thresholds into source cells. The circuit compares those thresholds with each line's width, so per-line widths still change at runtime, while editing a segment's width means recomputing the thresholds in JS.

**Does a paragraph ever get more lines when it gets wider?** Over 2,400 random plain texts across three engine profiles, with and without kerning, no: the line count never went up as the width grew, and no line start moved backward. Rich inline content is different, and this may be worth a look in pretext itself. In 71 of 80 random flows per engine profile, there's a band: a run of widths that lays out worse than the width just below it, with more lines or a line starting earlier. Most bands are exactly one `lineFitEpsilon` wide. In the smallest example, in the Blink profile, a 12 px "q" followed by a 20 px "-w", the item's own line walker fits "-w" within `availableWidth + lineFitEpsilon`, but `stepRichInlineLine` then checks `lineWidthContribution > remainingWidth` without the epsilon and wraps before the item. Bands of 1 px or more, up to 10.4 px, all involve soft hyphens. See [text-tabulated](text-tabulated/README.md).

**Fonts.** Headless checks used a fake canvas: widths on a grid of 1/64 of the font size, plus a non-dyadic run in text-tabulated (0 wrong decisions, widths drifting up to 1.8e-4 px). In Chrome with real fonts, text-walker's demo counted 0 mismatches against pretext over 236 states, and text-tabulated's demo counted 0 frames with a wrong line count, tight width, cursor, or line text over 2,473 frames.

## Findings worth taking back to the main runtime

These are suggestions for the morning. None were applied outside this folder.

Update, September 14, 2026: the index read instruction, `emitCompare` with rounding point records, and springs whose step matrix JavaScript writes into source cells have since been added to the repo root (see the update at the top of this README). The repo root's `window-manager.ts` and `photo-gallery.ts` weren't changed, so IndirectOS and its Photos app still use `emitSpring`.

- An integer index read, either as an instruction or as recognition of relu one-hots (index-read). It changes the cost of lists, text, and slot routing more than anything else measured.
- IndirectOS's springs integrate four substeps of the frame duration with a 32 ms clamp, so trajectories depend on frame rate and a stall loses time. spring-bank's fixed-step bank is cheaper (3,580 against 5,253 operations in its IndirectOS copy). It's frame-rate independent with deferred retargeting, and when presses fall between frames, with one extra evaluation at each press's timestamp.
- Declaring the spring timestep nonnegative where it's computed saves 320 operations with bit-identical outputs.
- Per-frame JS validation costs about twice the circuit today (about 70-80 µs against 33-40 µs). notation's validators derived from declarations cost about 1 µs.
- IndirectOS collapses a frame's pointer moves into the last one and fixes the order within a frame as down, move, up. input's queue, built for its own window circuit, handles every queued event up to a fixed number of presses per evaluation (55 layers for 32 events, against 281 when unrolled), with JS splitting frames that have more presses. Replacing IndirectOS's select chain with it wasn't tried.
- photo-gallery.ts's output validator rejects reachable animation frames: a thumbnail's left edge reaches -6.61 px while springing in after a viewport grows.
- notation suggests warning when `assume` narrows a wire that already has consumers. For integer bits inside large sums, input notes that the builder can't see locally how large a bit's ReLUs get, so a check would have to rely on declared ranges.
- NaN-aware range propagation, so gather lowering stays sound when a source cell holds Infinity.
- Marking rounding points in the builder. In six of the seven UIs, stored FP32 order mattered only at rounding points, so the executor, a GPU backend, or a notation could reorder and fuse the other sums. Settle tests and hit tests on drifting spring state still need rounding points of their own, e.g. quantizing a destination change to 1/64 px, and a value compared with its own stored copy needs the same arithmetic in both frames (exactness-budget).
- IndirectOS's stacking output adds `40 × animation.active` to the rank, where the activity clamps a sum over spring lanes of `100 × relu(|velocity| − 0.01)`. That amplifies tiny velocity differences and writes fractional z-index strings that CSS ignores.
- window-manager.ts's Photos clicks hit-test the animated layout, so which photo a click lands on depends on spring timing, while windows hit-test destinations (indirect-os-2).
- input's Tab, written through a counting bit with range peepholes, is 68 operations instead of 127 at 6 controls (learned-bits).

## Third round

After the first two rounds, three agents read the talk "Repeatable breakthrough" against tonight's results, each through one lens: a smaller unit of composition, homogeneity enabling uniform direction, and premature compression. Their notes are [notes/talk-smaller-unit.md](notes/talk-smaller-unit.md), [notes/talk-uniform-direction.md](notes/talk-uniform-direction.md), and [notes/talk-premature-compression.md](notes/talk-premature-compression.md). Each ran small scratch experiments before proposing anything.

What they noticed:

- The runtime's unit is already small, a wire computed by one atom, but most prototypes still built UI from larger units, and the biggest costs came from fitting those units into a fixed circuit: DOM slots (hn-thread's slot router is 25,616 operations), paragraphs walked line by line (at 1,023 segments, integer one-hots are 89% of text-walker's circuit, and each line adds about 8.75 layers), the frame as the only moment state changes (divergence between frame rates when presses fall between frames), and per-item code copied once per item (the gallery). Where the unit was already small and repeated, the approach was cheapest: one animated number is 4 products against a frame matrix that all springs share, a queued pointer move is about 46 operations, and one pixel of IndirectOS's press map is 458 operations.
- Several times, working one level below the usual unit gave a capability the unit couldn't express. Going below pretext's `layout(width)` call to the line walker's comparisons gave a different width per line, e.g. text flowing around a dragged window. Going below the frame to the 4 ms spring step gave frame-rate independence, with the timing conditions described above. Going below the widget to the pixel gave a map of which window receives a press at each of 1,024,000 pixels, in about 2 ms on the GPU through Dawn once the pixel coordinates are uploaded. Going below one-hot bits to a floor inside the executor gave reads that cost 1 operation.
- Because every compiled UI is built from the same three atoms over one source table, the lens suggests four operations that work on any of them with no code per feature: evaluate it over many instances, differentiate outputs with respect to source cells, instrument its decisions, and edit behavior constants that live in cells. Scratch runs tried the first two. One pushed 65,536 simulated users through 300 frames each of lab/event-window's circuit at about 250 ns per user-frame, with 0 mismatches for the 16 users also run through the oracle, and produced a tradeoff table for one behavior constant, the drag slop: the authored 4 px slop cancels 17% of clicks for users with 2 px of tremor, and no single slop served both steady and shaky hands. The other used candidate-gallery.ts, which scores three candidate layouts and shows the best one. For a request to make the hero image 60 px wider, one backward pass (3 to 4 µs) and one step changed two design constants held in source cells, the gap (14 to 13.56 px) and the rail maximum (280 to 221.3 px). But at 405 of 1,377 scanned viewports the top layouts tie, because each score is clamped at 1; there the gradient is 0 and a search has to take over. Instrumenting decisions and patching cells remain proposals, and patching only reaches constants that aren't folded into weights.
- Exactness may only be needed at rounding points. In a scratch interpreter over one scripted 240-frame IndirectOS session, reversing, balancing, or fusing every sum, or running in float64, flipped 0 of 64 booleans and 0 of 48 discrete state cells. Window positions and sizes drifted by at most 0.0022 px. The larger differences the scratch run reported as px, up to 0.59 when each mode ran on the reference's source tables and 1.8 when each mode drove its own state, with one 13.9 spike under reversed term order, turned out to be the windows' stacking output in z-index units (exactness-budget). Over that session, 2,039 of IndirectOS's 5,253 live values were exact bits in every frame, and 842 more were integers below 2^15.
- Bits as learned logic gates didn't work out of the box. A scratch differentiable logic gate network learned the Tab rule exactly for 2 controls, but reached at most 53 of 64 cases for 3 controls, 35 of 48 held-out cases for 4, and 458 of 896 cases for 6, while a counting construction from input's keyboard code handles 6 controls exactly in 127 operations. Many exact decisions tonight were a count followed by a threshold, e.g. Tab with disabled controls, the segment where a line overflows, and the row under the pointer, which suggests the counting bit, rather than the 2-input gate, may be the natural unit of learned behavior in this runtime.

Assumptions they flagged as possibly premature: the frame as the moment state changes; hit regions belonging to elements; the paragraph or message as the unit of text; outputs describing a whole capacity instead of what has arrived; per-item code copied per item; FP32 as the only numeric floor; the DOM as the output; strings and a grapheme vocabulary settled in JS; the index read as a special instruction (it's hard attention whose keys are positions); and circuits written by hand, when text-tabulated's black-box sampling absorbed every pretext feature with no feature-specific code.

Prototypes built from these proposals:

- [streaming-words](streaming-words/): a streamed chat reply where every word springs, a bubble is a reduction over words, and stopping a reply is one cell write.
- [user-population](user-population/): simulated users running input's window circuit as instances, to choose behavior constants such as the drag slop and the double-click interval.
- [drag-knobs](drag-knobs/): dragging any output edge of layout-tree's app shell changes the design constants held in source cells through a backward pass, with search when a decision blocks the gradient.
- [exactness-budget](exactness-budget/): perturbed executors over seven UIs, to find which exactness each actually depends on, and GPU shaders guarded only at rounding points.
- [event-time](event-time/): state committed per event, display frames that never write back, and all of IndirectOS predicted until the next event as keyframes.
- [pixel-output](pixel-output/): the HN thread drawn per pixel, with no DOM slot router.
- [learned-bits](learned-bits/): learning UI decision rules as 2-input gates versus counting units, with exhaustive certification.
- [code-points](code-points/): code points in cells, with advances and line break rules read from tables inside the circuit.
- [retiming](retiming/): one-frame delays chosen by search against a visible-error budget.

Two consolidation prototypes ran alongside them:

- [indirect-os-2](indirect-os-2/): IndirectOS rebuilt with the notation, the spring bank, the event queue, generated JS, and a Notes window whose text flows around the other windows.
- [instanced-items](instanced-items/): per-item programs written once and run as instances, with reductions between stages, applied to the gallery.

**indirect-os-2: do the wins compound?** The circuit got richer and stayed exact, but it didn't get cheaper. Each phase 2 change is a switch in one program, checked step by step: the notation base compiles identical to window-manager.ts (all 429 roots: 201 next-source values and 228 projected outputs); the spring bank gives 3,580 operations and 137 layers, or 91 layers with Photos reading stepped springs; a fixed-capacity event queue (8 slots, 2 presses per evaluation, keys routed to the focused window) gives 8,059 operations and 169 layers; and a Notes paragraph that flows around the other windows with a spring per word brings the whole program to 19,854 operations, 343 layers, and 49,900 stored weights, against the original's 5,253 / 192 / 11,598. The whole program matched a plain float64 oracle over 12,000 frames and 33,129 events, including 5,046 keys, and settled Notes layouts matched pretext's `layoutNextLineRange` on 150 random window arrangements.

- What compounded: the bank's savings added up across the other changes (1,353 operations with latches, 4,478 with Notes), and exactness held in the combined circuit.
- What interfered: the queue alone costs +4,476 operations and +78 layers, and its press sessions erased the depth that stepped springs had saved for Photos. Notes costs +11,795 operations and +174 layers, most of it the line walker and its integer one-hots.
- Cancellable clicks needed new semantics, which indirect-os-2's README calls judgment calls. Window buttons and dock items act on release, so pressing a close button, moving out past 4 px, and coming back cancels the close. Drags follow the geometry recorded at the press, so a window dragged past the edge and back returns under the pointer. Windows are clamped to the viewport at the end of each evaluation.
- Text should flow around where windows are going, not where they are drawn. With destinations as obstacles, 60 fps and 120 fps agree within 2.4e-4 px on a scripted session whose events all sit on 60 fps frame times; with animated geometry as obstacles, words differed by 25.4 px.
- Generated JS runs the whole program in about 29 µs against about 159 µs on the executor, but JavaScriptCore needed about 30,000 evaluations to optimize it, and the speedup falls from 14× for the original circuit to 5.4× for the whole program.
- Two findings about earlier code: window-manager.ts's Photos clicks hit-test the animated layout, so which photo a click lands on depends on spring timing; and spring-bank's declared range for window destinations (0..16,384) is false, since a dock item in a 2 px wide viewport is centered at -4.8e-7 px.

**instanced-items: write the per-item program once.** A staged builder over `Circuit` has shared stages, map stages written once and run per item, and reductions between them (sums, counts, prefix sums, first active, argmax, max, gathers, scatters), each with one stated FP32 accumulation order that both its JS loop and its circuit form follow.

- The gallery became 6 per-photo map stages, 233 operations per photo at any photo count. Expanded into one circuit at 221 photos, it is 55,627 operations and 64 layers, a little larger than gallery-circuit.ts (48,411 / 61) because per-photo constants turn from weights into products.
- Decisions matched native index.ts: 0 mismatches in about 2 million checks at 221 photos, 618,401 at 1,000 synthetic photos, and 2,408,107 at 10,000 with Brent-Kung prefix sums.
- The staged executor took about 65 µs, 310 µs, and 4,106 µs per frame at 221, 1,000, and 10,000 photos (2,222 µs at 10,000 on a quieter run), against 546 µs, 2,569 µs, and 43,027 µs for the duplicated circuit and 21 µs, 100 µs, and 3,055 µs for native index.ts. At 10,000 photos the duplicated circuit has 2.57 million operations and 5.6 million weights, takes 4.7 s to build, and needs about 2 GB of heap.
- Precision past a million pixels: with sequential prefix sums at 10,000 photos, the trace whose decisions all matched still had row tops off by up to 40.7 px and strip positions by up to 472.8 px, and the other trace flipped 74 decisions and diverged. Brent-Kung sums kept every decision equal to index.ts, with onscreen transforms within 0.23 px, so the parallel accumulation order was also the more precise one.
- The per-photo map stages ran bit-identical through wgpu and Dawn (0 differing values of 75 million at 10,000 photos through wgpu, and of 25 million over a shorter Dawn run), but uploading and reading back each stage made the GPU pipeline slower than the CPU executor (12.2 ms per frame at 10,000 photos through Dawn).
- Staging IndirectOS's small repeated parts made it bigger (6,282 operations and 215 layers against 5,253 and 192), because its thumbnail tables became per-item equality bits and products.

**streaming-words: every word springs, and a bubble is a reduction.** A word that hasn't arrived is a zero-width segment, so text-walker's walker needed no change: every arrived word got pretext's line and x in all 7,419 streamed states checked (48- and 96-word replies, 4- and 8-turn conversations, 1-character, 3-character, and whole-word chunks, three widths). Only outputs about the whole text read the arrived count, e.g. the line count is the number of line slots that start before it, which needs no read at an index. A turn change adds a large offset into the prefix sums to force a break, and each turn's bubble is a maximum over its words' right edges.

- Stopping a reply writes back 1 cell (the arrived count), or 2 when the press lands inside a word. Tried at every press time (3,555 Stops), no word before the growing word ever moved; the growing word itself went back a line in 54 of 1,043 chunked Stops at 240 px (about 5%), and never with whole-word chunks.
- Whole-word streams moved no visible word to another line. With 1-character chunks, 12 to 33 of every 1,000 chunks moved a word, always the growing one.
- Words fade in at their place rather than sliding from the previous word, which would have made the 8 of 48 words that start a new line travel about 210 px right where the reader is looking.
- A 48-word reply with its bubble and springs is 18,522 operations and 169 layers (about 115 µs on the executor, 25 µs with warmed generated JS); an 8-turn, 96-word conversation is 63,791 operations and 348 layers. The line walk's cost is unchanged from text-walker, and springs on spaces are about 90 operations per segment that a space doesn't need.

**user-population: the shipped circuit as a population simulator.** input's folded window circuit already kept the drag slop and double-click interval in source cells; giving the double-click distance its own cell left the circuit identical (1,494 operations, 1,280,000 outputs bit for bit). Each simulated user is a row of 143 cells, run through codegen's generated instance loop with its next state copied back per frame.

- 64 settings × 1,024 users × 600 frames: 39,321,600 user-frames at about 1.2 µs each, 0 mismatches over 1,228,800 comparisons of 32 sampled users against the one-event-at-a-time oracle, and 0 violations of one-hot, permutation, and workspace checks over every user-frame.
- At the highest simulated tremor (2.4 to 4 px), the authored 4 px slop, 500 ms interval, and 4 px distance cancel 76% of clicks and miss 97% of double clicks. The best slop per tremor level was 3, 4, 7, and 10 px.
- A 522-operation, zero-layer addition estimates each user's tremor from how far the pointer wanders during holds and selects that user's row of settings. In closed loop, over tasks after the first 5 s of use, the sum of four mistake rates went from 56.05% for the best single setting to 36.46%, against 34.79% for a table that knows every user's true tremor level (38.38% over the whole run, while the estimate catches up).
- This population was a poor test generator. Its traffic rarely put several events or two presses in one frame (72.6% of user-frames had no events, and 4 of 39 million had 2 presses), so a steady 60 fps population noticed 2 of 10 planted single-operation corruptions, and 6 with 2% janky frames, against 8 for input's random traces.
- Every rate describes simulated users whose hands were authored; no observation of people backs these numbers.
- 16,384 users × 600 frames ran bit-identical on the GPU through wgpu and Dawn, even without the max guard, because every product in this circuit is an exact integer.

**drag-knobs: drag an output, move the design constants.** Five design numbers of the app shell became source cells (card padding, grid gap, minimum card width, sidebar width, title font scale) for 60 operations and 1 layer. Dragging any rectangle edge seeds a gradient on that edge, backpropagates to the constants the designer unlocked, takes up to 3 steps, and searches 256 candidates as instances when a step doesn't reach the edge or adds overflow.

- Over 500 scripted drags, one gradient step solved 63.6% of moving frames (82.5% with every constant unlocked). About a quarter of moving frames (24.6%) started with gradient 0 for every unlocked constant, e.g. the right edge of a last-column card only moves with the viewport. A 16× heavier random search reached only 114 of the 1,121 unsolved frames.
- Straight-through booleans leak phantom slopes: through emitArgmax's comparison, 592 of 2,250 candidate-gallery gradients disagreed with finite differences with no decision flipping. Treating booleans as frozen (gradient 0) doubled candidate-gallery's one-step solve rate, from 16.5% to 38.2%.
- "What change flips this decision?" works from the builder's own difference wires when the decision is linear: 303 of 303 in-range predictions of a grid's column count held. Line counts are mostly out of reach of any one constant.
- Decisions flip far from the dragged edge: only 48 of 1,073 line-count flips were in the dragged card.

**exactness-budget: which exactness the UIs actually use.** An interpreter over compiled programs runs eight ways of adding terms (stored order, reversed, balanced, fused multiply-add, float64, and strict only at rounding points, plus combinations), open loop and closed loop, over IndirectOS, the gallery, hn-thread, lists' cards, text-editing, numeric-library's dock, life-calendar, and random circuits, each with its own reference checks.

- Reordering, balancing, and fusing sums changed no decision in IndirectOS (0 of 141,120) and changed one reference check across all the UIs: a gallery settle bit a frame late in 1 of 3,600 frames, which strict order at rounding points didn't prevent. Under fused order, drift in card positions also flipped 4 internal hit-test bits without changing any output.
- Running in float64 breaks every UI that rounds on purpose: 1,150,506 wrong rows, and as many wrong columns and days of week, in life-calendar; 5,736 of 12,000 card frames at 20 cards, 1,436 of 1,500 typing frames, 18,820 of 20,000 progress labels. Keeping stored FP32 order only at rounding points (1.6% to 61% of rows) and float64 everywhere else fixed all four.
- The one case where rounding points weren't enough is a value compared with its own copy from last frame: the gallery's settle test compares a destination recomputed this frame with last frame's stored FP32 copy, and at 50,607 px a float64 recomputation differs by 0.0105 px, just above the 0.01 threshold (108 index.ts mismatches). That needs the same arithmetic in both frames.
- IndirectOS's "13.9 px spike" from the third-round scratch run is the stacking output, not a position. The stack adds `40 × animation.active`, where the activity clamps a sum over spring lanes of `100 × relu(|velocity| − 0.01)`, so a 0.0035 difference in Photos' width spring velocity carried from earlier frames became 12.4 of the spike's 13.9 z-index units, and this frame's arithmetic added the other 1.5. It also writes fractional z-index strings, which CSS ignores.
- On the GPU, guards only at rounding points gave 0 decision mismatches through wgpu and Dawn on codegen's five instance workloads and 12 random circuits (the seven UIs above weren't run on the GPU), with far fewer guards: 537 to 84 for IndirectOS's press map, 787 to 30 for the shapes workload.

**event-time: commit per event, sample frames, predict the future.** Evaluations at each distinct event timestamp write the next state back; display frames evaluate a copy at the frame's time and throw its next state away; settle commits land at simulated times after the last event.

- Committed tables differed in 0 bits between 240 fps and 10, 30, 60, 120 fps and 500 ms and 2 s stalls, over 6 traces and 4 variants, and displays at shared timestamps differed in 0 bits. The earlier frame model with event-time evaluations was within 0.0093 px, but its written-back tables differed in about 1,000 of 6,117 frames.
- Idle costs nothing: no commits follow the last settle commit. A commit costs about 8 to 23 µs with generated JS.
- With the spring matrix to the power i in per-instance cells, all 301 samples from a commit, 4 ms apart up to the 300-step cap (1.2 s), run as one instance loop (0.36 to 1.21 ms), bit-identical to 301 separate displays, and bit-exact on the GPU with the max guard.
- In a model of how Web Animations play the emitted keyframes (not checked in a browser), predicted keyframes matched 240 fps displays in every bit at all 2,641 frames of each trace without a stall. Transform and opacity kept playing through a stall exactly when no event arrived between the last main-thread frame and the end of the stall, where held 60 fps frames were up to 688 px off. Width, height, and z-index still wait for the main thread during a stall, events inside a stall wait for JS, and a live resize created about 180,000 keyframe objects in 11 s.

**pixel-output: the HN thread drawn per pixel.** hn-thread's circuit without DOM slots feeds a per-pixel program that draws the container, sticky banners, gutters with hover emphasis, and text; codegen's planInstances split the thread logic (23,315 rows once per frame, 23,316 with the binary search's first probe) from the per-pixel part on its own.

- The slot router and its 25,616 operations disappear. Per pixel: 1,615 rows when the row under the pixel is a count over 251 rows, 314 rows with a binary search of 8 index reads, and 455 rows for real text, where the pixel searches the row, the line, and the character in pretext's lines and reads a 1-bit glyph atlas. Those lines add up to the circuit's breakpoint heights, so there's no second text layout.
- At 1280×800 through wgpu with the max guard, 0 of 6,144,000 outputs differed from the CPU and 0 decisions differed from an independent float64 painter's rasterizer, at about 16 to 20 ms per frame with readback for the binary-search versions. Without the guard, 1,245,968 of the 6,144,000 outputs differed in the settled state with bars (135,924 to 199,440 with glyphs).
- Both lookups assume sorted row tops; hn-thread's resize shift can make a row height negative, and then 1,728 decisions differ from the painter's order. The count version's guarded shader has 15,088 statements and took 4.6 s to compile cold in the latest run (up to 75 s in earlier runs on the shared machine).

**learned-bits: learning decision rules at the level of bits.** Eight tasks, each enumerated over every case: first active of 8 bits, Tab with disabled controls over 4 to 12 controls, a rectangle hit on 6-bit coordinates, click versus drag on 5-bit deltas, and one event slot of input's menu bar. Two unit types with equal parameter counts: 2-input gates (Petersen et al. 2022) and counting units (a count of up to 8 bits against a threshold, the form of most exact decisions tonight).

- Neither unit type learned any task exactly at base settings (0 of 48 runs), and held-out results trailed training results: the networks memorized cases instead of finding rules.
- Counting units got more cases right than gates on 7 of 8 tasks, e.g. 78,982 to 81,292 of 106,496 Tab cases at 12 controls, against 3,103 to 9,754.
- Sharing one counting unit's parameters across positions, like a shader run at every pixel, learned first-active-8 exactly from 60% of cases in 1 of 3 seeds, and gave the best held-out Tab results at 4 and 6 controls, though shared runs got fewer cases right than unshared ones at 8 and 12 controls. Tab was never learned exactly from part of its cases, and no network found the carry chain that a bit-level comparison needs, which integer arithmetic does in 9 to 11 operations.
- All 360 hardened networks compiled into circuits equal to their JS netlists on every case. A side result: input's authored Tab, rewritten through the same counting bit with range peepholes, went from 127 to 68 operations at 6 controls.

**code-points: code points in cells, break rules as table reads.** Each text cell holds one Unicode code point. Per cell, 8 index reads give the line break class and advance (two-level tables), three property bits, and a break bit from a 41 × 41 pair table over neighboring classes, all in 3 layers.

- All 1,114,112 code points decode exactly, and a 1,500-frame typing session with Chinese, Japanese, Korean, and Latin text matched a JS editor model.
- Against pretext's pre-wrap walker over 41,820 layouts, mismatches went from 8,806 with text-editing's rules to 215 with the pair table and CJK runs kept whole: 2,023 CJK and 1,620 Korean mismatches went to 0. Of the 215 left, 176 are a hyphen before digits, either between digits like `0-93` (140) or after a word (36), which pretext splits at the hyphen while keeping ` -5` whole, and two neighbors can't tell those apart. Another 26 come from pretext moving the space after an overflowing CJK unit to the next line.
- One key at 256 characters costs 42,326 operations with index reads, 22% below text-editing, when runs break anywhere; keeping CJK runs whole, the rule behind the 215, costs 47,808. The tables are 53,917 source cells, validated every evaluation (about 49 µs of about 447 µs). A font change rewrote 92 advance entries and no text cells.
- Out of scope: grapheme clusters (emoji sequences, combining marks), bidi, kerning and shaping.

**retiming: one-frame delays found by search.** A cut makes every row that reads a value read last frame's copy instead; a greedy search and minimum cuts pick cuts that remove the most layers for the least visible error, replaying traces closed loop.

- None of tonight's hand-chosen cuts fits a 1 px budget: Photos reading last frame's content size and opacity costs 88.9 px at 60 fps and 161 px at 10 fps with IndirectOS's original springs; the app shell reading last frame's sidebar spring costs 1,380 px and 116 decision mismatches.
- A search on one trace overfits: IndirectOS with the spring bank reached 84 layers at 0 px on the live resize trace, and then broke with over 7,000 mismatches on random traces, since a trace only tests values that change in it. Searched on scripted plus random traces, the critical-values strategy took its longest chain from 136 to 123 layers with 0 px and 0 mismatches on three held-out random traces, while the minimum-cut set at the same depth failed on one of them (996 px, 33 mismatches).
- A delay's error is how far the delayed value moves in one frame, so px budgets need a statement of input speed. Chains with a decision at every stage, like the gallery's click-to-occlusion chain, shed almost nothing.

Proposed but not built tonight: routing presses by reading a per-pixel owner map instead of hit-testing in the scalar circuit; a design atlas of design variants × viewports as instances, searching for ties and reflow jumps; decision margins as one uniform output that says where a circuit is fragile, to direct reference checks; behavior edits as cell patches an agent can make without recompiling, and what lifting the remaining constants into cells costs; candidate futures (several next source tables evaluated as instances, one committed); and field morphs, where every pixel's signed distance springs toward the next UI state.
