## Runtime additions since September 14, 2026

On September 14, Cheng chose the recommended option for three runtime questions ([decisions 1 to 3](ui-exploration/guide/review-and-decisions.md#decisions-for-you)). Every existing circuit compiled to the same program with the same values, e.g. HandwiredOS stayed at 5,253 operations in 192 layers until the changes below.

- **Index reads.** `circuit.indexRead` and `circuit.indexReadAffine` copy `candidates[floor(index)]` in 1 operation at any table size, for an index range strictly inside ±2^24. A gradient into the index throws unless the caller passes `'zero'` or `'backward-difference'`. The `recomputeDepths` option recomputes layers after gather lowering, and is off by default ([index reads](../docs/execution-model.md#index-reads), [compilation](../docs/execution-model.md#compilation)). The option is off by default because it changes existing programs: with it on, the candidate gallery stays at 60 layers, with operations moved between them (moved here from docs/execution-model.md on October 15, 2026).
- **Comparisons.** `emitCompare` builds an exact bit of `>`, `>=`, `<`, `<=` or `===` from declared ranges: integer bits when both operands lie on grids declared with `assumeGrid`, e.g. 2 operations in 2 layers for `a >= b` on a 1/64 grid, and a sign cascade otherwise, e.g. 15 operations in 14 layers for `a >= b` within 0..16,384. `emitMinimumExact`, `emitMaximumExact` and `emitClampExact` select one operand with such a bit, and `emitFirstActive` counts these bits and index reads of bits as proven bits ([comparisons](../docs/execution-model.md#comparisons), [grids](../docs/execution-model.md#grids)).
- **Rounding points.** The builder records boolean atoms, `emitCompare`'s operations, and operations marked with `markRoundingPoint`, so a backend may reorder or fuse every other sum ([rounding points](../docs/execution-model.md#rounding-points)).
- **Springs and time.** host-timing.ts counts 4 ms spring steps and writes a 4-number step matrix per stiffness and damping pair, which `emitApplySpringMatrix` and `emitAnimatedObject` apply. `advanceFrame` steps springs to each event's timestamp before applying the event, snaps objects onto their destinations past 300 steps in one frame, and with `'events and settle checks'` writes state back only at events, settle checks and snaps ([springs and time](../docs/execution-model.md#springs-and-time)). Springs that stored absolute positions, the form until September 14, 2026, measured on spring-matrix.test.ts's traces: with `'events and settle checks'`, positions stayed within 8.1e-5 px of float64, against 7.4e-5 px for stored displacements, and with the traces moved to 65,536, 131,072 and 1,048,576 px, 42 to 48 of 48 runs settled differently from float64 at each offset, up to 40 runs were still animating at the end, and positions were up to 16.6 px off (moved here from docs/execution-model.md on October 15, 2026).

## HandwiredOS on WebGPU, and where a browser frame goes, September 16, 2026

Measured with scratch files outside the repo, in headless Chrome 153 through Metal and in Bun 1.4.0, on an Apple M5 Max at load average 4 to 6. These numbers predate the [engineering guide pass](#engineering-guide-pass-september-17-2026), which e.g. cut cells.ts's validator in a Chrome drag frame from 277 to 12.7 µs, and they weren't measured again. One evaluation of HandwiredOS took 2.2 ms on WebGPU, the compute pass alone about 1.9 ms, against 81 µs on the CPU executor in Bun and about 140 µs in Chrome, because one table's statements run one after another in a shader. With codegen's guards against Metal regrouping sums, all 177,154 outputs of 202 recorded tables matched the CPU executor. The result arrived 5 to 7 ms after the frame callback started, after the callback had returned, so it could only be drawn a frame later. Many independent tables in one batch take less time on the GPU from about 16 to 28 tables, e.g. 4.8 ms against 335 ms in Bun at 4,096 tables, but a frame's 1 to 5 evaluations each read the state that the evaluation before wrote back, so they can't run as one batch. [codegen](ui-exploration/codegen/README.md)'s WGSL executor writes a program as one shader, and HandwiredOS's 6.4 MB shader didn't finish compiling in Metal in 28 minutes, so a scratch executor split the shader into 24, which compiled in 8.1 s without a shader cache. The program isn't what limits a frame either: on the real page, dragging Files over Notes kept the main thread busy for about 2.0 ms of each 16.7 ms frame, of which `machine.step` took 1.1 ms and running the program about 0.75 ms, and no frame was dropped. patterns.md's [When a tree takes less time than the loop](../docs/patterns.md#when-a-tree-takes-less-time-than-the-loop) says where a GPU did take less time.

## Term order probe, September 17 to 18, 2026

An ordinary sum adds its terms in wire number order, and wire numbers follow the order of the builder's statements, so moving a statement can round a fractional sum differently. Cheng's point was that correctness needs one deterministic order that every evaluator shares, not statement order in particular. A probe in a worktree, never merged, sorted each sum's terms by a content key of each operand, i.e. a hash of how the operand is built, instead of by wire number. The switch changed no decision, i.e. no output that only ever holds 0 or 1, in any scripted session of HandwiredOS, standalone Photos or the candidate gallery, and changed open-loop values by at most 1.2e-4 px, e.g. in Photos' thumbnail geometry, and stored spring velocities by at most 2.5e-3 px/s. Decisions differed only for inputs aimed within a few FP32 steps of a fractional boundary, e.g. 0 to 272 of 168,000 such clicks in standalone Photos, depending on the hash's salt. Moving statements stopped changing values: 7 builds of HandwiredOS with moved statements had 0 differing values. But an edit to how an operand is built started to matter instead, e.g. swapping the two arguments of one `emitMultiply` in photo-gallery.ts, which changes nothing under today's order, changed 232 of 877 root keys and 4,198 to 17,061 root values in their last bits over a 5,721-frame session, so "the outputs are bit-identical" would stop working as the check for an optimization edit. Today's HandwiredOS is also barely sensitive to statement order: 1 of the 6 moves changed any value, since `roundAffine`, products, selects and springs keep the order written in the call, and pixel geometry is on the 1/64 px grid, where sums are exact. The decision: not switched. The two issues the probe found that hold today are in the list below.

## The JSON highlighter and regex search over many documents on WebGPU, October 13, 2026

Cheng asked whether regex search or the JSON highlighter, or both in one app, becomes clearly faster on the GPU. [lab/json-search](json-search/README.md) answers with both programs of [src/json-search](../src/json-search/README.md) over 100,000 generated JSON documents of up to 512 code points, each program written as one step that a shader loops over a document's positions, in headless Chrome 155 through Metal on an Apple M5 Max. A review of the folder then corrected its first answer, which had claimed more than the measurements show ([what the review found](json-search/README.md#what-the-review-found-and-what-changed)). The four answers below are those of October 13, 2026. The search's times changed the day after, see the update at the end of this section.

- Against the same programs on the CPU: yes, from about ten documents on, by 200 to 25,000 times. For 100,000 documents that are already on the GPU, the highlighter's pass takes 2.2 ms and a search of a pattern of up to 8 states 7 to 8 ms, when evaluations follow each other. On the CPU the highlighter takes 2 s as generated JavaScript and 8 to 9 s on the executor, and a search 14 s as generated JavaScript, or 24 s when its loops run all 512 positions of every document as the GPU's do, and about 3 minutes on the executor.
- Against plain JavaScript on one thread, for validating and highlighting: only as a repeated pass. With the documents already on the GPU, the highlighter's pass takes less time than JSON.parse from about 10,000 documents on, e.g. 0.65 ms back to back and 2.6 to 3.4 ms after a pause, against 7 to 10 ms. But a document's result only changes with its text, so a page needs the pass once, and from the texts the GPU's answers for 100,000 documents arrive after 0.13 s, where a plain JavaScript highlighter takes 0.12 to 0.15 s.
- Against RegExp on one thread, for regex search: about even. A pattern of up to 8 states takes 7 to 8 ms when searches follow each other and 17 to 21 ms after a pause of 200 ms or more, which is what a page that searches per keystroke gets, against 12 to 43 ms for RegExp. Longer patterns are slower than RegExp, 64 ms up to 16 states and 0.87 s up to 32, since a step reads a table once per pair of states. Only on a pattern that makes RegExp backtrack, `([a-z]+)+x`, is the GPU clearly faster, 7 to 21 ms against 2.1 s.
- Against JavaScript in 8 workers: no. RegExp counts a pattern's matches in 2 to 7 ms, and JSON.parse validates the documents in 11 ms.

Writing each program's step once inside a shader loop took the shader's compile from 107 to 130 s to 0.05 to 0.11 s for regex search, and from 2.3 s to 0.04 s for the highlighter. Every value read back from the GPU equals the CPU's, including at the capacity, at the maximum depth and for patterns that fill a program. Why an evaluation after a pause takes longer wasn't found. searcher.ts is the module that the page "Search 100,000 JSON documents" of [the demo site](#the-demo-site-october-13-2026) searches with, on the GPU or, behind the same interface, on the CPU. Not done: a cheaper search step for 16 and 32 states, and any other GPU or browser.

Update, October 14, 2026: a second code writer, bit-emit.ts in src/json-search, writes the shaders of the three search programs, and the page's searches run them. The search program as written didn't change, and no compiled program changed: it is still weighted sums, ReGLU gates and index reads, and the CPU runs it as before. The first writer, loop-emit.ts, writes every operation as one f32 statement. bit-emit.ts holds a value as an integer or as a bit where the program's declared ranges, grids and exact bits prove that the value is a whole number or a bit, and writes the table reads that one gate combines as one AND of two 32-bit words. Measured in headless Chrome for Testing 155.0.8059.79 on the same machine, at load averages of 2.5 to 23, one search of 100,000 documents takes 4.6, 4.7 and 5.2 ms for a pattern of up to 8, 16 and 32 states when searches follow each other, where loop-emit.ts's shaders take 7.8, 69 and 945 ms, and 11 to 16 ms after a pause of 200 ms or more ([the measurements](json-search/README.md#measured-results-the-searcher-with-bit-emittss-shaders)). So the cheaper search for 16 and 32 states, which the paragraph above lists as not done, is done: the search program's step is as it was, and only the code that is written for the GPU differs. The answers above change for the search as follows:

- Against the same programs on the CPU: by 200 to 40,000 times.
- Against RegExp on one thread: no longer about even. RegExp counts the matches of ten ordinary patterns in 8 to 43 ms. When searches follow each other, the GPU takes 1.5 to 9 times less on every one of them. After a pause, it takes less on seven of them, about the same on one, and more on two, a date and `connection reset`, which take RegExp 8 to 9 ms. A longer pattern is no longer slower than RegExp, and the pattern that makes RegExp backtrack takes 5 to 12 ms against 2.1 s.
- Against JavaScript in 8 workers: still no. RegExp's 2 to 7 ms there is about what the GPU takes when searches follow each other, and the GPU's time after a pause is 2 to 8 times as long.
- From the texts, the GPU's answers for 100,000 documents arrive after 0.15 s, where they arrived after 0.13 s, since the three search programs are built and compiled in that time too. bit-emit.ts's shaders compile in 0.02 to 0.03 s each, and the page compiles all three when it loads.

The highlighter's shader stays loop-emit.ts's, since its pass didn't get faster from the other writer. Any other GPU or browser is still not done.

## Reusable layout

Run `bun run start:reusable`. The demo compares ordinary wrapping, search for each layout, and the shared learned rule. Controls change viewport width, collection, item count, and captions. All methods keep reading order and required content; scrolling is allowed.

Under the authored preference objective, the shared rule transfers well to new counts and widths and leaves a visible gap with longer captions and unfamiliar crops; the loss table is in the experiment's [results](reusable-layout/README.md#results). This is learned responsive sizing within a fixed flow layout, not generation of arbitrary page structures. The wrapping baseline uses a fixed preferred width; we have not shown that the model beats a carefully tuned responsive formula or measured how much it improves on a width-only model. Every method has zero measured missing items, text overflow, horizontal overflow, and overlap in those sets. Resize sweeps still find abrupt reflow. ## Correctness changes

- Whole multiplication and selection retain their meaning for differentiation while expanding to the existing forward atoms. Multiplication at zero now has the intended derivative in either operand order. Boolean surrogate gradients require an explicit option.
- Selection uses two masked products, avoiding overflow from subtracting large finite candidates.
- `roundAffine` preserves evaluation boundaries, constant and duplicate terms, and term order through inlining. Ordinary `affine` remains a simplifiable builder expression.
- Numeric bounds follow rounded FP32 operations and account for overflow. Min/max no longer claim ideal mathematical bounds where their arithmetic can drift. Their preserved rounding and weaker bounds cost some additional layers and live operations.
- The trace compiler propagates returns, rejects mutations in runtime conditional expressions it cannot safely handle, and compares nullable values correctly. Its source interpreter is independently checked against native JavaScript; intentional FP32 drift is reported separately.
- Real-source compiler tests use a verified historical source fixture. Compatibility with the latest external file is an optional `--live` check, not an assumption that another repository remains unchanged.
- Layout fitness includes direct parameter derivatives. The event demo retains queued and browser-coalesced pointer moves, including outward-and-back movement that cancels a click.

See [execution semantics](../docs/execution-model.md), [macro contracts](../docs/execution-model.md#macro-contracts), and the regression tests for exact domains. This is not a proof of all possible circuits or all JavaScript programs.

- **Many paragraphs on the GPU**, September 17, 2026 ([lab/ui-exploration/text-walker](ui-exploration/text-walker/README.md#many-paragraphs-on-the-gpu-september-17-2026)): Cheng asked whether pretext's layout, with lots of paragraphs, is faster on the GPU than on the CPU. One program per paragraph size breaks lines the way pretext's `layout()` does for plain text, at a width in a cell, with a fixed number of line slots and named outputs when a paragraph needs more. At 517 segments and 83 line slots, with integer one-hots, the walker that Notes used until October 13, 2026, it is 113,802 live operations in 684 layers, with index reads 27,634 in 518, and as the segment walker, which has no line slots, 8,244 in 4,646. On the CPU every formulation takes longer than pretext's 2.5 µs per long paragraph: 10.5 µs as generated JavaScript for the segment walker, and 198 to 683 µs on the executor. codegen's WGSL executor ran the segment walker over up to 100,000 paragraphs in one compute pass in headless Chrome, and all 102,764,544 checked line counts and 10,688,998,499 compared during timing matched pretext. When only the width changes and the cells stay on the GPU, the GPU takes less time than pretext in Bun from about 170 long or 800 short paragraphs, e.g. 3.88 against 287 ms at 100,000 long paragraphs. When the texts change, it takes less time from about 1,400 long or 8,700 short paragraphs, and only 1.7 to 1.8 times less at 100,000, since writing the cells in JavaScript and the upload take most of the time. One long paragraph takes about 200 times as long on the GPU, 0.39 ms against 2 µs. Line counts are exact for widths on the 1/64 px grid, and a width off that grid within float32 rounding of pretext's fit limit can give one more line. This item's times of pretext were measured with pretext 0.0.9. pretext 1.0.0, which the repo has since October 14, 2026, lays out the same paragraphs in 3.2 to 4.8 times less time in Bun, with the same line counts, and the GPU wasn't timed again ([the update of October 14](ui-exploration/text-walker/README.md#update-october-14-2026-pretext-100)).
- **Knuth-Plass line breaking**, September 17, 2026 ([lab/knuth-plass](knuth-plass/README.md)): Cheng noted that pretext has a Knuth-Plass demo, and that optimal line breaking is a shortest path over break points, which fits min-plus matrix products combined in a tree. A plain JavaScript reference and two programs pick the breaks with the smallest total cost for up to n break points and W boxes per line, with min(slack, 63)² per line in whole pixels and 0 for the last line, since the demo's own cost divides by a runtime space count. The chain form takes one step per break point, the tree form combines W × W min-plus matrices with Brent-Kung's network, and both follow the chosen pointers by doubling. Every value is an integer within 2^24, so costs, pointers and breaks equal the reference exactly on random paragraphs with ties, the reference equals every set of breaks on small paragraphs, and pretext's demo gives the reference's breaks on text where the two costs agree. At n = 1,024 and W = 32, the chain is 277,068 live operations in 10,232 layers and 2.9 ms per evaluation in Bun, the tree 2,823,382 in 230 layers and 22 ms, with 7.4 GB of RSS while building, and the JavaScript reference takes 75 µs. On the CPU executor, the tree takes 1.7 to 7.7 times the chain's time at every measured size. A page shows pretext's greedy breaks next to the program's, 4 evaluations per frame in 1.6 ms for the chain and 9 ms for the tree in headless Chrome, and an export writes leaf matrices and expected results. Later the same day, WebGPU kernels in headless Chrome ran the tree one level per dispatch, for up to 10,000 paragraphs at once. Every entry is a u32, so the GPU gives the reference's totals and pointers exactly for paragraphs of up to 270,532 break points, a check in Chrome matched the reference at that size, and 502,812 timing readbacks matched. With the positions or the widths uploaded, one paragraph on the GPU takes about 0.3 to 0.6 ms at every size up to 4,096 break points, longer than the reference's 1 to 303 µs, but less than the chain program from about 174 to 387 break points. A kernel over every entry, W³ sums per product, doesn't cross over at W = 16 and 32, e.g. 42.3 ms against 10.4 to 22.5 ms for the JavaScript loops at 1,000 paragraphs and W = 32. A kernel that multiplies only the rows that hold costs, with the paragraphs' positions uploaded and the line costs computed on the GPU, takes less time than both JavaScript loops in Bun from below 30 to about 190 paragraphs of 256 break points, e.g. 4.50 against 18.2 and 10.4 ms for 1,000 paragraphs at W = 32. The count depends on W, the loop and the Chrome session, since near 100 paragraphs one evaluation is mostly the round trip to the GPU, which changed about 2 times between sessions. Uploading line costs computed in JavaScript never beats the typed-array loop.

## Still open

The next interpreter question is whether fractional training examples identify the required addition grouping. Scaling to longer programs without a complete loss table, learning a search guide across task families, and discovering shared query/key functions remain untested. The data-adapter baseline supplies a small exact task and independent oracle for that next comparison.

For UI, the next evidence should come from broader content and an explicit human task, not from interpreting synthetic preference scores as usability. GPU execution, a general JavaScript compiler, learned arbitrary abstractions, and a full learned UI runtime are not delivered by these experiments.
