# Runtime costs

`bun lab/runtime-cost/report.ts` compares literal reference execution, the existing tensor executor returning a full wire array, and the tensor executor with reusable buffers returning only requested outputs. A two-operation coordinate transformation also has a direct scalar-JS baseline. The UI circuits do not have independent handwritten baselines in this study.

Each measurement reports the median of seven samples, rotates method order, warms each method, and consumes all requested outputs. Checksums must agree across methods. This is steady-state CPU execution on an unchanged input, not event processing, GPU execution, compilation, or a browser frame benchmark. Repeated input avoids mixing state transitions with evaluation cost; the reusable evaluator's changing-input correctness is tested in `numeric-semantics.test.ts`.

The reusable evaluator is an opt-in API: `circuit.createTensorEvaluator(roots)`. It captures a compiled program and returns a function whose output array is overwritten on its next call. Callers that retain a frame must copy the output. Existing evaluators retain their old ownership behavior.

The purpose is to measure simple allocation and output-copying costs before pursuing a more elaborate layer scheduler. Timings depend on the machine and concurrent work; rerun locally rather than treating a single ratio as an architectural guarantee.

Update, September 16, 2026: timing several programs in one process can distort later timings. The executor stores its indices in `Uint8Array`, `Uint16Array` or `Uint32Array` arrays depending on the program's size, so once programs of different sizes have run, the executor's typed-array reads become polymorphic, i.e. each read handles several array types. In July 2026, [gather-lowering's benchmark](https://github.com/chenglou/handwired/blob/exploration-2026-09/lab/gather-lowering/README.md) measured later timings distorted by up to 10 times this way, which once reversed its comparison between a program with gather lowering and the same program without. It then ran each program in its own process and reported the spread of the per-process medians, since the same program still landed in one of two JIT states from process to process, e.g. 19.6 to 43.5 µs for one configuration. `report.ts` runs its three circuits in one process.

Update, October 14, 2026: `bun lab/runtime-cost/layers.ts` measures what a layer costs on the CPU executor besides its operations. It builds the same 16,384 sums of two terms as chains of 64, 1,024 and 16,384 sums, so that the compiled program has that many layers, and times each layer count in a process of its own. In Bun 1.4.3 on an Apple M5 Max, at a load average of about 4: 54 to 55 µs per evaluation in 64 layers, 64 to 65 µs in 1,024 and 210 to 214 µs in 16,384, about 10 µs per 1,000 layers, which docs/patterns.md's introduction quotes. Until this day the probe was a scratch file outside the repo, and it timed the three layer counts in one process, where 1,024 layers took 82 to 86 µs.
