# JSON highlighter

A monospace text box, highlighted on every keystroke by one numeric program. It holds up to 512 code points. JavaScript writes each code point, the text's length and the caret into cells. The program returns what every character is shown as (whitespace, punctuation, key, string, escape, number, literal, error, or after the text), the first error's position and kind, whether the text is too long, whether the first error is nesting past the maximum depth, and the bracket that matches the bracket at the caret. The highlighter started on September 17, 2026 in lab/json-highlighter, as a demo of a traditional JavaScript task, to see how the approach handles it. It moved into src/ on September 18, 2026 as the repo's second app, with identical programs, and from src/json-highlighter into src/json-search/highlighter on October 14, 2026, as one of the two programs that JSON search runs.

Every capacity is fixed while building, and what doesn't fit has a named output. The capacity is 512 code points and the maximum depth is 16, two constants in kinds.ts, and the numbers in this README are for them unless they say otherwise. From October 13 to October 14, 2026 both were parameters of `buildHighlighter`, for the highlighter's own page, which built 2,048 code points at depth 13. The page was removed on October 14, 2026 and the parameter after it, since JSON search builds only 512 code points at depth 16, and 7f2a905 is the last commit that has the parameter, its tests and the measurement script's two arguments for it. Past 512 code points, the program reads the first 512, `truncated` is 1, and the first error is `tooLong` at 512 unless an error comes first. An opening bracket at depth 16 is the error `tooDeep`, and `depthExceeded` is 1 when `tooDeep` is the first error. An earlier error hides nesting past the maximum depth, e.g. `x` on the first line followed by 17 `[` reports `unexpectedCharacter` at 0 and `depthExceeded` 0. Any text within capacity costs the same: on September 18, 2026, evaluating an empty text takes 122 µs in Bun, and writing and evaluating a full text 123 µs, of which the writes take about 2 µs ([results](#results)).

## What the program computes

Each stage runs over 513 positions: the 512 cells, and position 512, which is the end of the text, or the 513th code point of a longer text.

1. **A character class per position.** `classes[codePoint + 1]`, one index read from 129 cells. The empty cell value -1 reads `end`, and every code point from U+0080 up clamps to the entry of U+007F, `other`, which is only allowed inside strings ([patterns.md, "A loop over data that rarely changes"](../../../docs/patterns.md#a-loop-over-data-that-rarely-changes)).
2. **The tokenizer.** A state machine of 26 states over 33 classes, e.g. `hex2` after two hex digits of a `\u` escape, or `fal` after the letters of false read so far. The `'loop'` form reads `lexerNext[state × 33 + class]` once per position. `'brent-kung'` and `'sklansky'` turn each position into a table of 26 reads and combine tables with one read per state ([patterns.md, "A state machine over queued events"](../../../docs/patterns.md#a-state-machine-over-queued-events)). One more read per position gives the event, e.g. `stringStart` or `badNumber`, from the state before the position and its class.
3. **Depth before every position.** Running totals of +1 for `{` and `[` and -1 for `}` and `]` events ([patterns.md, "Running totals"](../../../docs/patterns.md#running-totals)), as a chain or a prefix network.
4. **The container kind at the current depth.** JSON's grammar needs a stack, e.g. to know whether a comma leads to a key or a value. At a bounded depth, the stack's kinds fit in one integer whose bit d − 1 is 1 when the container at depth d is an object:

   ```js
   // familiar: a stack of container kinds
   if (character === '{') stack.push('object')
   if (character === '}') stack.pop()
   const inObject = stack.at(-1) === 'object'
   // the program: a running total, and one comparison with the bit of the current depth
   code += character === '{' ? 2 ** depthBefore : character === '}' ? -(2 ** (depthBefore - 1)) : 0
   const inObject = code >= 2 ** (depth - 1)
   ```

   The weight is one index read at `depthBefore × 25 + event`, and the comparison is `emitCompare` on integers, 2 operations ([expressions.md, `a >= b`](../../../docs/expressions.md#familiar-expressions)). The code is exact before the first error, since every container below the current depth is still open and every closer matched its opener's kind, so no bit at or above the depth is set. After the first error the code can be wrong, e.g. `[}` subtracts a brace's bit that was never added, but the grammar reads nothing after its first error. Weights reach 2^15 at depth 16, so the code stays within ±511 × 2^15. At positions 1 to 510, the code minus a level weight of up to 2^15 stays below 2^24, and `emitCompare` builds integer bits. At position 511 the difference can reach exactly 2^24, one step past what integer bits allow, and `emitCompare` builds a sign cascade of 17 operations, which is also exact. `circuit.roundingPoints()` reports 5,127 integer bit operations and 17 sign cascade operations in every form, and a test checks both counts. In general every comparison is an integer bit while capacity × 2^(maximum depth − 1) is below 2^24, e.g. at 2,048 code points and depth 13, where `roundingPoints()` reported 20,489 integer bit operations and no sign cascade on October 13, 2026, while the capacity and the maximum depth were parameters. One more level reaches exactly 2^24 at the last position, as 512 code points at depth 16 do, and past that the positions from 2^(25 − maximum depth) − 1 on get sign cascades, e.g. 26,129 such operations at 2,048 code points and depth 16, in a program of 86,584 operations with the same outputs, built on the same day.
5. **The grammar between tokens.** A state machine of 8 states, e.g. `keyOrClose` after `{`, over 88 symbols, `token × 8 + depthClass × 2 + inObject`, where the depth class tells the top level, depth 1, depths 2 to 15 and depth 16 apart. Built as a loop or a prefix scan like stage 2. Strings in a key position lead to the state `colon`, so a string character is shown as a key when the grammar's state after it is `colon`, one read per cell at `event × 8 + grammarState`.
6. **The first error.** The grammar's `error` state never goes back, so the bits `[state after the position === error]` read 0...0 1...1, and their count of zeros is the first error's position ([patterns.md, "`findIndex` when the test flips once along the items"](../../../docs/patterns.md#findindex-when-the-test-flips-once-along-the-items)). Every position computes an error kind, the lexer's kind of its event plus the grammar's kind of its step, and the first error's kind is one index read at the count.
7. **The matching bracket.** Brackets pair by depth, whatever their kinds. An opener's match is the closer just before the first later position whose depth before it is at most the opener's depth before it, and a closer's match is the last earlier position whose depth before it is below the closer's. Each position computes whether it's such a hit, `[depthBefore <= threshold]` and on the right side of the bracket, then a running count of hits gives the first hit as the count of `[hitsThrough < 1]` bits and the last hit as the count of `[hitsThrough < totalHits]` bits. Two `emitFirstActive` trees gave the same answers in 9,241 operations in the loop form, and the count in 6,687.

The rules that go past JSON's grammar are written out at the top of [reference.ts](../../../tests/json-search/highlighter/reference.ts), e.g. the first error's position is the first code point at which the text stops being the start of some valid JSON text, so `[1 2]` reports `expectedCommaOrClose` at 3, and `[1` reports `unexpectedEnd` at 2. After a lexer error, e.g. the `x` of `[x]`, the rest of the line shows as an error, and tokenizing starts again after the next line feed, so later lines keep their colors. The bracket at the caret is the code point before the caret when it's a bracket, otherwise the code point at the caret. The caret cell holds 0 to 513, so a caret past code point 512, e.g. at 600 in a text of 699 code points, has neither code point among the cells, and no bracket is at the caret.

## What fit well

- A tokenizer is already a table-driven state machine, so its tables moved into cells unchanged, and the loop form reads 3 tables per position: the class, the next state and the event.
- The first error is a count, since an error state that never goes back gives bits that flip once. Its kind is one index read at that count.
- The reference and the program were written separately, from the rules at the top of reference.ts, and agreed on the first run. JSON.parse checks the reference's validity, and table corruptions show the comparison can fail.
- The cost doesn't depend on the text: an empty text and a full text take about the same µs, 122 and 123 in Bun on September 18, 2026, with about 2 µs of writes, which is the worst case a keystroke can hit.

## What got awkward

- **The stack.** No entry in patterns.md or expressions.md covered a stack while this demo was built. The integer code in stage 4 works for two reasons that the construction depends on: the grammar ignores everything after its first error, and at 512 code points with a maximum depth of 16, the code's range of ±511 × 2^15 barely fits, while the page's 2,048 code points at depth 13 fit with one bit to spare. `emitCompare` builds integer bits at every position except 511, where the code minus the level weight reaches exactly 2^24 and it builds a sign cascade of 17 operations. Depth 17 needs weights up to 2^16, whose totals pass 2^24 from about position 255 on, and `emitCompare` would build sign cascades of 17 or more operations there instead of 2.
- **Prefix scans cost much more than the loop here.** The tokenizer has 26 states, so each combine is 26 reads: Brent-Kung is 18 times the loop's operations for the tokenizer, and 2.5 times its µs in Bun for the whole program on September 17, 2026, or 3.1 times on September 18, 2026, 385 against 123 µs: the executor change of September 17 took about 32 µs off the loop form's 1,043 layers, and Brent-Kung's 81 layers measured the same as before. patterns.md says operations cost more than layers on today's CPU executor, and this demo measures that at 26 states.
- **Fewer operations didn't give fewer µs.** Replacing the two `emitFirstActive` trees with the running count removed 2,554 operations from the loop form, but the count is a chain that starts after the depth totals, so layers went from 574 to 1,043, and µs stayed about the same, 141 before and 148 after. Each layer costs the executor time too.
- **Grids on index reads.** Index reads get no inferred grid, so every read that feeds `emitCompare`, e.g. a depth change or a level weight, needs `circuit.assumeGrid(read, 1)`. Without it, `emitCompare` builds a sign cascade with no warning. `circuit.roundingPoints()` tells which construction each comparison built, e.g. by counting its `'sign cascade'` entries, and execution-model.md's Rounding points section documents it, but expressions.md's `a >= b` row and its Decision bits section didn't point to it while this demo was built. This demo first counted operations instead, and missed the sign cascade at position 511 described in stage 4.
- **createEvaluator on a program without state.** The program keeps no state, but `createEvaluator` checks all 4,575 cells before and after each evaluation and returns every cell's next value, most of them constant tables: 173 µs against 155 µs for `circuit.createTensorEvaluator` on the outputs only, or 140 against 123 µs on September 18, 2026. Since October 13, 2026 `createHighlighterMachine` compiles the outputs itself and checks the cells once, with `built.validate`, before each evaluation: 128 against 141 µs at the default limits in Bun, and 520 against 555 µs at the page's limits. The page reads the compiled program's size from the same compilation.
- **Error recovery is part of the behavior.** Showing the rest of an error line as an error, and starting again after a line feed, is part of the tokenizer's tables and had to be copied in the reference's scanner, as did which bracket at the caret counts and when a string is a key.

## Notes on the docs

- patterns.md's state machine entry used `sklanskyPrefix` from the guide example's prefix-networks.ts, which src/runtime didn't export, so this folder copied the file. The prefix networks are now in src/runtime/prefix-networks.ts, which this folder imports.
- The same entry's cost, O(S × k log k), is Sklansky's. Brent-Kung gives O(S × k), and with a constant initial state, only entry 0 of each prefix that starts at position 0 is live, so measured counts come out below S times the number of combines.
- expressions.md's `table[index]` row doesn't say that a read has no grid, which execution-model.md's Grids section does. The row is where a reader looks before comparing a read value.
- patterns.md's "`findIndex` when passing items can be anywhere" points to a tree. When the first and the last hit are both needed, a running count of the hits and two sums of monotone bits gave both in fewer operations here.
- tutorial.md builds around state cells and `advanceFrame`. A program that is a function of its inputs, like this one, uses neither, and the tutorial doesn't say what to leave out, e.g. that `table.finish()` works with no state cells.
